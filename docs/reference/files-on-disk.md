# Files the apps keep beside themselves

## File-handling Rules

- `config.json` (next to each exe) — per-app settings: `server_url`, `client_id`, `theme` (`system`, `dark` or `light` - deliberately not admin-gated, since it changes what this screen looks like and nothing else), for the Storekeeper also `storekeeper_name`, and for Notifier also `current_user`, `poll_interval`, `setup_complete` and the two popup timers `popup_dismiss_secs` and `popup_repeat_mins` (#194), each read through a clamping reader rather than off the dict, this being a file on the engineer's own machine and those two being timers on the window they are asked through. `member_id` is written on both clients by the check-in that first learnt one and is what lets a Notifier find its Engineer again after the name above has been corrected at the console (ADR-0016) — `current_user` is then replaced with whatever the server says that id is called now, which is the one setting here a client adopts rather than owns, the way `storekeeper_name` is. A file that cannot be written costs the adoption until the next tick and nothing else. `storekeeper_name` is not set here and is not editable here — it arrives on `GET /health` and is written back so the two entries that bracket a run, `app.started` and `app.stopped`, can be attributed before the first heartbeat has been answered. `client_id` is written the first time the app checks in and read back on every later start, which is what makes a renamed machine one installation rather than two. A file that cannot be written costs the identity at the next launch, not the check-in: the identifier is generated once per run either way, because one minted per tick would fill Connected Clients with a row every fifteen seconds for a single machine.
- `client.log` / `client.log.1` (next to each client app) — this installation's own System Log, one line per action, written whether or not it reached the server. A rolling pair: the current file is started afresh once it passes 256 KB and the previous generation is kept, so a client spends at most ~512 KB on it however long it runs. One line is `ts  LEVEL  event  detail`, then `  [actor]` where there is one, then the entry's `data` as one trailing JSON object where there is one (#072) - the same document the server is shipped and stores in `system_log.data`, serialised with sorted keys and dropped whole where it exceeds `detail`'s own 400-character cap, so a line never holds half a document and the file stays one line per entry. It is **not** trusted to match the server's copy and is not read back by anything — it is what an engineer's laptop can still say about itself when the server cannot be reached, the same reason `applaunch.py` writes `launch.err.log`. Never holds a password: `common.log_event` is only ever handed an event name and a line of context.
- `asset_cache.json` (next to the app that calls `common.fetch_asset_types()` — currently the Storekeeper alone) — the last asset types the register actually answered with, plus when, and since S2 the last **Asset Models** it answered with as well, one entry per Asset Type under a key folded to lower case (027's fold, so two spellings of one Type cannot become two entries free to disagree) and one for the unnarrowed list. Both writers **read-modify-write**, for the reason `_save_server_cfg` does: the types fetch wrote a fresh dict until S2, which would drop every model on the 15s tick that refreshes the types — the cache then answering nothing at exactly the moment it is read, which is a server that cannot be reached. The models half has **no baked-in fallback**, unlike the types: an empty list is a real answer there (a Type nobody has recorded a model against, which is what the console shows too) and is cached as one, where an empty *types* answer is a server that has not answered properly and leaves the cache alone. A convenience, never an authority: rule 6 is enforced on the server regardless of what this holds, and a submit still goes to `GET /lookup` rather than to this file. A fetch that succeeds replaces it; one that fails leaves it exactly as it was, so a client shows a two-day-old list rather than the baked-in fallback the moment the server cannot be reached — the shape `sync_server_cert` already uses for the certificate. It holds no credential and nothing per-person, so it joins the never-backed-up, never-shipped files beside `client.log`.
- `update.log` (next to each client app) — what the two halves of an update wrote down, and the only thing an engineer can send back when one fails: phase two runs under `pythonw.exe` with no console and no Tk, so an exception there is otherwise as silent as the `ImportError` `launch.err.log` exists for. Appended to rather than rolled — an update is a handful of lines a few times a year, not a stream — and it holds no password, being handed nothing but file names, versions and a digest. Nothing reads it back.
- `update_result.json` (next to each client app) — what the applier decided about the update that brought this install here, and the whole of the handover between the two phases (#148). Phase two is a process that imports nothing of ours - it is overwriting `common.py` while it runs - and by the time it has an outcome there is no app left holding a log queue, so the System Log entry it cannot write is written by the app that starts next: `common.report_update_result` reads this file beside `app.started`, ships `update.applied`, `update.failed` or `update.rolled_back` carrying **both versions and the SHA-256 of the package**, and **deletes it only once the entry has actually been queued**, which is what `log_event`'s answer is for - an outcome lost to a failed log write and one reported twice are both worse than reporting it a start late. It is in no manifest, so an update leaves it exactly as it found it, the way `config.json` and `update_state.json` are left. An outcome this build does not know is cleared rather than reported, since left behind it would be read on every start for ever; a file that cannot be read at all is cleared too, there being nothing in it to report. It holds no password, being handed nothing but versions, a digest and a sentence. Deleting it by hand costs that one entry and nothing else.
- `update_rollback\` (next to each client app) — every file the incoming manifest is about to overwrite, put aside before a byte is written and restored whole if the app does not come back up. `lib\` is **moved** into it rather than copied, the way `installer.py` replaces that directory wholesale: it is a few hundred files, and a half-merged one is rule 13's mismatch with nothing left to name it. Replaced by the next update, so one generation is kept - which it now is: `rollback` is named after the version being **replaced**, so the one subdirectory the applier used to clear was a name that had never existed on that machine, and each update left a whole vendored `lib\` beside the last, for ever. `_clear_old_generations` empties the directory instead, the incoming generation's own name included. It runs **before** a byte of the install has moved, which is the only moment at which nothing is at risk: what it removes is copies of files that are live in the install right now, where doing it after a successful update would put the deletion inside the very window the next sentence is about. Nothing ever read the older ones - a restore comes from `update_rollback\<from_version>\` and from nowhere else, and that is always the build currently installed. `tools/client-checks.py` holds the count, and holds the kept generation to being the build that was replaced. Deleting it between updates costs nothing; deleting it *during* one is how a failed update stays failed.
- `app.ico` (next to each **source-mode** client app) — the Desktop shortcut's icon, and nothing else reads it. Written by the installer through `ui_kit.write_ico` rather than shipped in any package: the artwork is drawn at runtime by the apps themselves, so a file in a bundle would be a second copy with nothing holding the two together. A shortcut takes its icon from its target and in source mode that target is a signed `pythonw.exe` (rule 12), so this is what stops an engineer's Desktop carrying Python's feather. There is none in an exe install, which needs none. Deleting it costs the shortcut's icon at the next repaint and nothing else; a reinstall writes it again.
- `admin_config.json` (next to the server) — `{password_hash, first_run, capability_hashes, capability_holders}`. Read into `ADMIN_CFG` at import and **re-read from disk where something outside this process has written it** (`_sync_admin_cfg`, asked by `_admin_password_ok`, `_authorise` and `_update_admin_cfg`), because the import-time snapshot is right only for the one deployment where the console *is* the server: under IIS and under the Windows Service the Server GUI is a second, monitor-only process, so **Change Admin Password changed the credential the console checks and left the one the network checks as it was** until the app pool was recycled - which is every door on the wire, `POST /admin/verify` above all, so an installer standing up a Storekeeper went on being let in by the install-time `admin` and refused the password the Admin had just set. The same gap points the other way, a legacy hash the serving process rewrote on use being invisible to the console. It is `storekeeper_can_cancel`'s rule applied to the credential - a thing an Admin changes must not need a restart to take effect - and it is a **stat** rather than a re-read, so an ordinary request pays one stat against a file that has not moved. A file that has gone unreadable **leaves the in-memory copy exactly as it was**, which is not the raise below pointing the other way: that one refuses to fall back to the install-time default, and this one refuses to fall back to anything at all. The read is **merged over the defaults**, so a build that adds a key still loads a file written before it existed — which is exactly what a file written before `capability_hashes` existed does: no key means no delegation, `{}`. Both `password_hash` and every value in `capability_hashes` are stored as `pbkdf2_sha256$<iterations>$<salt>$<hash>` — the salt and the iteration count are in the value, so nothing beside it says how to check it and raising the work factor invalidates nothing (ADR-0008). A **bare 64-character hex SHA-256**, which is what a file written before ADR-0008 holds and what the two writers outside `server.py` still write — `installer.py` during a server install and `tools/dev-run.ps1` seeding a local run, neither of which can reach the salted helpers (rule 10) — still verifies and is **rewritten in the salted format on the first use of the password it stands for**; that in-place upgrade is the third writer of this file, alongside the admin changing their password and a capability password being set or cleared, and nothing else writes it. **`installer.py`'s write is a read-modify-write on a reinstall** (#153): `password_hash` and `first_run` are the two keys the operator was asked about and everything else in the file is kept, `capability_hashes` being exactly what a fresh dict dropped — the rule `server_config.json` beside it already had — and a file that cannot be read is left byte for byte alone with the install saying the admin password was not applied, rather than replaced by the two keys this install happens to know about. **Every writer inside the server goes through `_update_admin_cfg`, which syncs, writes the file and only then updates `ADMIN_CFG`** - the order rather than the merge, since the in-memory copy is what every door is checked against; it syncs first so the read-modify-write is over what is on disk now, a console writing a capability password out of a stale copy having put back the admin password hash it was still holding. Each caller set the key and then saved, so a write that failed left the credential changed in memory and unchanged on disk with nothing said at the time: the Admin's correct current password was then refused by Change Admin Password, the hash it was checked against being the one nobody had been told about, and a restart put the old password back. An install directory the console account cannot write in is how that happens, and saving first means a failed write changes nothing anywhere. A malformed file raises on purpose rather than falling back, which would silently reset the admin password to its install-time value; a `capability_hashes` that is present but is not an object raises for the same reason, since reading `{}` out of a corrupt map would drop every delegation the admin had made on a server that then looked healthy. `capability_holders` beside it is the name the Admin wrote against each capability password (R1) and is read the same way and raises the same way, for a weaker version of the same reason: a corrupt map costs the names in every `remote.action` entry written afterwards, which is the whole of what ADR-0015's identity half buys. A file written before it existed has no key and the merge above answers for it. Only the hashes are stored — the passwords themselves are nowhere on disk.
- `server_config.json` (next to the server) — `{host, port, db_path, ssl_enabled, feed_limit, refresh_secs, storekeeper_can_cancel, storekeeper_cancel_window_mins, storekeeper_name, theme, smtp_host, smtp_port, smtp_from, smtp_starttls, smtp_username, notify_rules, sync_base_url, sync_list_path, sync_list_key, sync_auth, sync_username, sync_interval_mins, sync_mapping}`. `db_path` is read at import to derive `DB_PATH`, so its assignment sits **below** `_SERVER_CFG` in `server.py` and not with the other path constants; an absent or empty value means `DB_DEFAULT_PATH` beside the server. An invalid one does **not** fall back — the error is kept and `_require_db()` refuses to start, because a server quietly writing to a different file than the one configured is the worse failure. `host`/`port` need a restart; the display settings and the Cancel switch do not — the switch is re-read from this file on every request. A missing `storekeeper_can_cancel` means allowed, so a file written before it existed is normal rather than corrupt, and unlike `admin_config.json` this one does not raise on an absent key; `storekeeper_can_add_engineer` is the same shape, the same read-on-every-request rule and the same absent-means-allowed answer (ADR-0017), deliberately rather than by accident — two switches of one shape answering an absent key two different ways is the kind of fact that gets remembered wrong; `storekeeper_cancel_window_mins` beside them is read from disk on every request for that same reason and **answers an absent key with zero** (#198), which is the other answer and is deliberate: a switch nobody wrote down means the freedom that was there before it existed, where a duration nobody wrote down is no window at all, and anything that is not a whole number above zero reads as off, this being a setting that opens a door; a missing or empty `storekeeper_name` is read the same way and means `STOREKEEPER_DEFAULT`, which is the `transactions.storekeeper` column default — the two have to agree, or a row written by an old Client and a row written by a server with no name set would read as two different people. Every writer inside the server goes through `_save_server_cfg(**changes)`, which read-modify-writes: overwriting the whole file drops `ssl_enabled` and turns HTTPS off on the next restart with both cert files still on disk, so nothing looks wrong until a client fails to verify. **There are three writers outside the server.** `tools/install-iis.ps1` records the `port` it bound the IIS site to so the GUI and IIS agree on one number rather than the GUI probing a port nobody serves and starting a second Flask on the default; it read-modify-writes for the same reason, touches `port` alone, leaves an unreadable file alone rather than replacing it, and writes no-BOM UTF-8 because this file is read back with a plain `open()`. `tools/bind-port.ps1` is the newest (069, ADR-0021): it is the elevated half the Server GUI spawns when an Admin saves a new port, and it writes the same key the same way for the same reasons — the difference between the two being that this one moves the binding the number names rather than standing the site up. `installer.py` is the third: a Server install creates this file, and a **reinstall read-modify-writes `port` alone** out of the field it asks for — the same shape and the same reason, an unreadable file left alone there too rather than replaced, with the success popup saying the port was not applied. `notify_rules` is the list of `{event, to, level}` an Admin set in Notification Rules (031), read from disk on every log entry and normalised as it is read, so a rule that was edited by hand into something unreadable is ignored rather than able to break a log write. The five `smtp_*` keys are the mail settings (030) and are read from disk on every send rather than from the import-time snapshot, the way the Cancel switch is: an Admin who has to restart the server to point it at a different relay will not reach for the setting in the situation that made them want it. A missing one means nothing is configured, which is a server that sends no mail rather than a corrupt file. The seven `sync_*` keys are the external asset system (032) and are read from disk on every run for that same reason, `sync_mapping` being the `{field: JSON key}` map an Admin typed over the guess and an empty one meaning the guess stands. **No password and no hash is stored here, and that sentence survived mail and survived the sync** — every checkable password lives in `admin_config.json` in the salted format ADR-0008 defines, and the two **replayable** secrets, the SMTP password and the external system's credential, are in `smtp_secret.dat` and `sync_secret.dat` below precisely so that the three scripts which read-modify-write this file are never holding a ciphertext they might rewrite (ADR-0013, ADR-0014); the keys above are the whole of it.
- `smtp_secret.dat` (next to the server) — the SMTP password, encrypted with **Windows DPAPI at machine scope**, written and read by three helpers in `server.py` and by nothing else — which is still true since 032 gave the sync a secret of its own: those three name `SMTP_SECRET_PATH` and are wrappers over the path-taking `_secret_set` and `_secret_get`, so the DPAPI calls are written once and each file still has exactly one set of helpers that knows its name (`sync_secret.dat` below, ADR-0014). It is the first secret here that is **not** a one-way hash: ADR-0008's values are compared against and this one is **replayed** at every send, so it has to be recoverable. Machine scope rather than user scope because one install is opened by three different accounts — the interactive Admin at the Server GUI, LocalSystem under the Windows Service, and the app pool identity under IIS — and a secret only one of them can read is mail that works while somebody is logged in and stops silently when they are not. A file of its own rather than a key in `server_config.json`, which `install-iis.ps1` and `installer.py` read-modify-write and `dev-run.ps1` stages: a ciphertext is not a setting. Where DPAPI is unavailable nothing is written at all and the password is **refused** with the reason named — never a plaintext fallback, because this file travels in every backup and every `rollback/<version>/` copy of the install. Restoring the install onto a different machine leaves a file that cannot be decrypted; it reads as no password rather than raising, and the Admin sets it again. **The console's own Backup / Restore therefore leaves it out altogether and names it** (A13, ADR-0019): a copy that cannot be decrypted where it lands is a file that reads as a stored password and is not one, so the backup carries neither it nor `sync_secret.dat`, the manifest records why, and the restore says both have to be entered again. Deleting it costs the stored password and nothing else. **Since #172 it has a second setter and still no reader**: `POST /admin/mail` writes it through `_save_mail_settings`, the same one writer the console's window calls, so the DPAPI refusal is in one place and a machine that cannot encrypt refuses a remote caller with `no_secret_store` exactly as it refuses the Admin - while `GET /admin/mail` answers whether one is stored and never what it is, which is what keeps the write side safe to delegate. The three helpers are still the only functions that name this file. See ADR-0013.
- `sync_secret.dat` (next to the server) — the external asset system's bearer token or basic-auth password (032), encrypted the same way and for the same reason: it is **replayed** on every run, so it has to be recoverable, and machine scope is what makes a scheduled run under the app pool identity read the same secret the Admin set at the console. **A file of its own rather than a second value in `smtp_secret.dat`** — the two secrets are unrelated and rotate on different schedules, clearing one must not be able to take the other with it, and a corrupt file should cost one feature rather than both. The DPAPI calls themselves are written once: `_secret_set` and `_secret_get` take the path, and the three `_smtp_secret_*` helpers and the three `_sync_secret_*` helpers are wrappers naming one path each — a second hand-copied `CryptProtectData` is what rule 10 exists to prevent, and a security primitive is the worst thing here to hold two copies of. Where DPAPI is unavailable nothing is written and the credential is **refused** with the reason named, exactly as the mail password is; and a credential is never sent over a plain `http://` base URL at all. It is excluded from a console backup beside `smtp_secret.dat` and for its reason (A13, ADR-0019), and named in the manifest as something to set again. Deleting it costs the stored credential and nothing else. See ADR-0014.
- `iis.json` (next to the server, on an IIS install only) — `{site, app_pool, port, cert_thumbprint, install_dir, configured_at}`: what `tools/install-iis.ps1` recorded of the site it stood up. **Its presence is the whole signal that IIS hosts this install**, which is what `_iis_host` answers off and what `tools/update.ps1` reads to decide which of the two hosts to stop; missing, unreadable, not JSON, or JSON that is not an object all mean "not IIS", and mean it quietly, because a server that has never met that script has to behave exactly as it did before this file existed. Read `utf-8-sig` and it stays that way: until 054 it was written with a BOM, and fixing the writer rewrites nothing already on disk. **It has a second writer since 069** — `tools/bind-port.ps1` read-modify-writes `port` alone, the port being a fact this file states and that script being what moves the binding it names (ADR-0021). `bind-cert.ps1` writes nothing here on purpose: which certificate is bound is not among the facts recorded. Deleting it makes this install read as not-IIS to the GUI, to the banner and to `update.ps1` alike.
- `maintenance.json` (next to the server) — what a backup or a restore left on disk while it runs: what is running, since when, the process id and who started it (G3, ADR-0018). Read from disk on **every** request, the way `storekeeper_can_cancel` is and for a sharper version of its reason - what enters the state is an operation on a worker in this same process, and a request arriving a moment later has to see it. A file of its own rather than a key in `server_config.json`, which `install-iis.ps1` and `installer.py` both read-modify-write: a server held shut by a value one of those could rewrite is a server shut for a reason nobody typed. **An absent, unreadable or shapeless file means no maintenance**, which is the behaviour before this existed and the opposite answer from `admin_config.json`'s raise - a stray byte there silently resets the admin password, where a stray byte here is a server refusing every write with nothing able to say why, and this state is a few minutes long where a credential is permanent. On disk rather than in a global so a crash mid-backup leaves something an Admin can look at; the price is a file outliving its process, which `_start_background_jobs` clears at start and writes down that it cleared, that being the one moment such a file is **known** to be stale. The monitor-only GUI does not go through that path on purpose: a window watching somebody else's listener has no business clearing that process's state mid-operation. Deleting it by hand takes the hold off, which is the manual way out.
- `pending_answers.json` (next to the Notifier) — the Confirms and Rejects this engineer has given that the server would not take yet, one entry per Transaction, each `{action, id, reason, why}`. The Held answers bullet above is what it is for and what the three answers are. Shipped by nothing and read back by this app alone. Deleting it loses those answers, which is the failure it exists to prevent.
- `restore_aside\` (next to the server) — what a restore copied aside before it replaced anything, one directory per run named for the moment it ran (A13, ADR-0019). `update.ps1`'s `rollback\` shape, and the only way back from a restore somebody pointed at the wrong backup. Unlike `update_rollback\` beside a client it is **not** cleared to one generation: a restore is a rare, deliberate act, what it holds is a handful of small files rather than a vendored `lib\`, and the moment somebody wants the previous one is the moment after a second restore has been run. Nothing reads it back — putting a copy back is done by hand, by somebody who has looked, the same answer `update.ps1` gives for the database it sets aside. Deleting it costs every earlier restore's way back and nothing else.
- `cert_rollback\` (next to the server) — the certificate and key that were live immediately before a cutover (C4, ADR-0020), copied aside before either is replaced and the only way back from one. **One generation**, which is `update_rollback\` beside a client rather than `restore_aside\` above: a restore is a rare, deliberate act whose earlier copies are worth keeping, while what is in here is a **private key**, and every generation kept is another copy of the one file that must never travel (rule 1). The directory is emptied before the copy, so the generation that is kept is the pair that was live a moment ago, which is the only one anything could be rolled back to. Nothing reads it back — putting a pair back is done by hand, by somebody who has looked, the same answer `restore_aside\` and `update.ps1` both give. Deleting it costs the way back from the last cutover and nothing else.
- `assets.db` — SQLite database. Next to the server unless `db_path` moves it, which needs a restart. It is the only file here that can move: the lookup sheet, both config files and the certificate are part of the install, not of the data. Every tool that touches it resolves the configured path (`Resolve-DbPath` in `tools/_deploy.ps1`) — a backup written where the database no longer is, is worse than no backup, because it succeeds and is the wrong file.
- `asset_lookup.xlsx` — the Lookup Sheet as a file, next to the server. Since 024 it is **not the store**: the assets live in the `assets` table (ADR-0011) and this is the seed a first run reads them in from, written out of the embedded copy by `_ensure_sample_lookup`. It is not rewritten when an asset changes and goes stale on purpose — what `GET /lookup/file` serves is generated from the table, not read from here. Deleting it costs nothing on a server whose table is already seeded.
- `ssl_cert.pem` — the server's **public** certificate. Lives next to every app: the server serves HTTPS with it, and each client trusts it explicitly (`load_verify_locations`) because it is self-signed. **The Server GUI's Server Settings window exports a copy of it** (C5) through `_export_public_cert`, which refuses a source holding a `PRIVATE KEY` and writes only the certificate blocks — the one supported way to get this file off the server by hand, precisely because `ssl_key.pem` is the file beside it. Clients receive it from the installer, which takes it from a copy placed beside `AssetManager_Setup.exe` — the one place it looks, 061 having stopped building one in and #155 having removed the branch that went on looking for it — and afterwards refresh it hourly from `GET /cert`, over the connection their current copy already verified. A client that was given none fetches it once on first contact and pins it only if a person confirms the fingerprint — see ADR-0010; that fetch is the only unverified connection any client makes, and the hourly refresh is not it. The **server** package carries it too, best effort: `package.ps1` takes it from `-CertPath`, else `<installDir>\ssl_cert.pem`, else `GET <baseUrl>/cert`, and **warns rather than failing** when none of the three answers — the public half only, and packaging refuses anything that turns out to hold a private key, however it arrived. Nothing on a build machine mints one since 061 took `package.ps1 -SelfSigned` out: `install-iis.ps1 -SelfSigned` generates and binds in one run on the server, and a build machine's key was never the one the server binds. A client whose copy is missing has no *trusted* channel to fetch over, which is why the bootstrap is answered by a human rather than by the network: the installer is still the way to supply it without anyone having to read a fingerprint.
- `ssl_cert_next.pem` / `ssl_key_next.pem` (next to the server) — the certificate the console has staged and not bound (C1, ADR-0020), and the key that goes with it. Written by `_stage_new_cert` and by nothing else; read by the Server Settings window, to show the staged fingerprint beside the live one. **Nothing in the request path resolves either name** — the listener is bound to `ssl_cert.pem`, `GET /cert` serves `ssl_cert.pem` — which is exactly what makes staging safe. `ssl_key_next.pem` is the same file as `ssl_key.pem` one certificate earlier: never packaged, never exported, and named in a backup's manifest as something deliberately left behind (ADR-0019), a key nothing has bound yet being still a key. `package.ps1` and `bundle-client.ps1` refuse it by the name rule they already carry. Deleting the pair costs the staged certificate and nothing else — Generate writes another.
- `ssl_key.pem` — the server's **private** key. It belongs on the server machine. Never bundled into the installer and never placed in a release package: both are copied to engineers' laptops, and anyone who unpacked one could impersonate the server. It reaches the server from next to the installer during a server install or through the Server GUI's Server Settings upload button. Since 061 took `package.ps1 -SelfSigned` out, no build machine mints one at all: `install-iis.ps1 -SelfSigned` generates and binds on the server, so the key is never written off that machine.

When `getattr(sys, 'frozen', False)` is True, all paths are relative to `sys.executable`. When running as a script, they're relative to the script's directory.
