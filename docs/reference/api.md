# HTTP API

## API Endpoints

**Every one of these that is not a GET can answer `503` with
`code: "maintenance"`**, and it is written here once rather than on each row
because it is one fact about the server rather than twenty about endpoints: a
backup or a restore holds writes for the length of the operation (G3, ADR-0018)
and `_hold_writes_during_maintenance` answers before any view runs, so there is
no route below that opts into it or out of it. What decides which are held is
`MAINTENANCE_OPEN`, the set of non-GET endpoints that stay **open** - three of
them, and none writes anything a backup is about: `admin_verify`, `auth_verify`
and `preview_import`. Written as the open set rather than the refused one so a
route added later defaults to being held, and `tools/server-checks.py` fails a
non-GET route that is in neither. **Reads are untouched**, which is what makes
it a maintenance state rather than an outage. `503` rather than `409` because
that is what a client already treats as the server rather than the row - a
client built before the code reads the refusal correctly without knowing it -
and the code is what lets one that does know it stop after the first, this
answer being the same for every write behind it.

**The Credential column is derived rather than written.** Every route in
`server.py` carries a `door(...)` line naming the credential it asks for
(#209), and `tools/cascade-audit.py` holds this column against those
declarations - so a route whose credential moves and whose row does not is
caught here rather than by whoever tries the endpoint. `open` is a route that
takes no credential **on purpose**, and the reason is written at the route
itself rather than only in an ADR; `own` is the Engineer's own password
(ADR-0009), which the admin password also opens. A capability label beside
`admin` is a capability password that reaches the route over HTTPS and nothing
else (ADR-0015), and `open · admin · <label>` is the two routes that stay open
**until** a password is offered - `POST /members`' create-only path (ADR-0017)
and `POST /transactions/cancel`'s Pending path (ADR-0002).

| GET    | `/health` | open | Heartbeat, total records, `port` (the port actually being served), `next_port` (a saved port awaiting a restart, else null), `storekeeper_can_cancel` and `storekeeper_name`. **Additive only** — this is how every Client resolves the server and how the port-change cascade works, so a field may be added here but never renamed or dropped: a stranded client cannot be updated until it can reach the server. `storekeeper_can_cancel` **absent means allowed**, which is the behaviour before the switch existed, and `storekeeper_can_add_engineer` beside it is read the same way for the same reason (ADR-0017). `storekeeper_cancel_window_mins` is deliberately **not** read that way and the difference is the setting: a switch nobody has written down means the freedom that was there before it existed, where a *duration* nobody has written down is no window at all — so **absent means zero**, which is also how it is switched off, the file and the form saying the same thing by one number rather than by a number and a flag (#198). `storekeeper_name` is the bare name the Admin set — the `(Storekeeper)` a System Log entry carries is a label and wording it here would put it in the `storekeeper` column of every row that Client submits — and **absent or empty means nothing said**, so a server that predates the key leaves a Storekeeper recording under the name it already had rather than blanking it. `ssl` is what is in front of this **port** rather than what this process was configured to do (070): where `iis.json` is there it is `_iis_tls_bound()` - the same answer the console's banner and the Remote Admin door already read, the thumbprint `install-iis.ps1` recorded or, where it recorded none, a TLS handshake against the port on loopback - and otherwise the `ssl_enabled` flag with both `.pem` files present. Same key and additive in meaning, for the reason above - under IIS TLS ends at the site (ADR-0001), `ssl_enabled` is written by the console's own certificate install and by nothing else, and `ssl_cert.pem` correctly is not there at all where `install-iis.ps1` bound from `-PfxPath` or `-CertThumbprint`, so the flag answered `false` over a site serving https. `seen_from` (#242) is what `_client_addr()` resolved this very request to - a diagnostic for `deploy-checks.ps1` and an operator on a machine that is not the server, not a value any client reads, and additive for the same reason as every other key here. `port_locked` (#267) is `true` only when this process was launched by IIS's HttpPlatformHandler (`%HTTP_PLATFORM_PORT%` is set) **and** `iis.json` is absent — IIS set up by hand rather than through `install-iis.ps1`, so nothing recorded which site owns the binding and no cascade can move it. `next_port` is withheld (stays `null`) in that one case; where `iis.json` **is** present the 069 flow is unaffected and `next_port` is advertised exactly as off IIS. The Server GUI's Server Settings window (a separate process from whichever one holds the port) reads `port_locked` off a loopback call here, since its own environment never carries `%HTTP_PLATFORM_PORT%` |
| GET    | `/cert` | open | The server's public `ssl_cert.pem`, or 404. Clients refresh their copy from here |
| GET    | `/cert/next` | open | The **staged** certificate `ssl_cert_next.pem`, or 404 with `code: "no_staged_cert"` where none is staged, which is the ordinary state. What a Client fetches on the `trust_cert` command (C3, ADR-0020) and appends to the file it already pins, so it accepts both while the old one is still what is served. A route of its own rather than a parameter on `/cert`, because the two answer different questions and only one of them is what ADR-0010's first-contact bootstrap may pin from: this is a certificate bound to nothing at all. No credential, for `/cert`'s reason — a certificate is public and a staged one is less than public; the **key** beside it is served from nowhere (rule 1) |
| GET    | `/version` | open | `{latest, has_installer, download_path, client_packages}`. Clients compare against their `APP_VERSION` and prompt to update when behind. `client_packages` is **additive** like `/health`'s keys: one entry per client zip this server actually holds, keyed by the app's own name (`notifier`, `storekeeper`) and carrying `{filename, path, sha256, size}` - a client built before it reads the keys it knows and goes on offering the installer. The digest is over the zip's own bytes and is cached against its mtime and size, so a launch poll does not re-hash eight megabytes; it is what the updater checks a finished download against **before the running app is stopped** |
| GET    | `/download/installer` | open | Serves `AssetManager_Setup.exe` if present next to the server (404 otherwise) |
| GET    | `/download/client/<key>` | open | One client app's release zip out of `dist\` beside the server - `<dist>\<version>\` first, then `<dist>` itself, the same two shapes `update.ps1` looks in, and only at the **published** version, since that is what `/version` told the client to ask for. `key` is looked up in `CLIENT_PACKAGES` rather than joined onto a path, so no name a caller sends reaches a file this does not already know about. **No executable crosses it** (rule 12) - the zip holds `.py` files, the launchers and the vendored `lib\`. 404 with `code: "no_package"` where this server holds none, which is what a client gets on a server whose `dist\` nobody copied the bundles into |
| GET    | `/transactions?member=<name>` | open | List, optionally filtered by member. Takes the same `include_cancelled` opt-in as `/export`, for the same reason Every. row carries `origin` (`desktop`, `auto`, or null where it was decided before Origin existed or is still Pending) - additive, an older Notifier ignores it (#282). |
| POST   | `/transactions` | open | Create. **No auth** — see ADR-0002. Required: `team_member`, `direction`, and at least one of `asset_number`/`serial_number`. Auto-approve members are confirmed immediately. Forwards to `_create_transaction`, which is also what the Server GUI's Add Transaction calls (rule 6). **A `timestamp` in the body is ignored** — the row is stamped by the server. The endpoint is unauthenticated, so a caller who could set the timestamp could rewrite the store's history from anywhere on the network, and dating an entry outside the 24h Auto-Accept window would confirm it without asking anybody. Backdating is a parameter of the helper, passed only by a caller that has already proved the admin password. **`notes` is capped at `_TXN_TEXT_MAX` (500) and truncated rather than refused** — the endpoint is unauthenticated, so its length is a caller's choice the way every field of `POST /clients/checkin` is, and `transactions` has no retention bound at all: `LOG_MAX_ROWS` bounds the System Log's row count and `LOG_RETENTION_DAYS` its age, and one enormous row walks past both. Truncated because the movement already happened and the record is owed — a long note must not be what refuses it. The cap is in `_create_transaction`, the one writer, so the Server GUI's Add Transaction and the offline buffer's flush are held to it too |
| POST   | `/transactions/cancel` | open · admin · Manage Transaction History | Body: `{id, reason, cancelled_by?, password?}`. **No auth for a Pending Transaction while the switch is on** — see ADR-0002 and ADR-0003. Retracts a Transaction whose movement never happened; the row is kept, marked, carrying who/when/why. `reason` is required. The **admin password** is what opens a Confirmed Transaction, and it also overrides the Storekeeper switch; a nameless admin is recorded as `Admin`. **Since #198 there is one Confirmed row a caller with no password may retract** — an `auto_approved` one, inside `storekeeper_cancel_window_mins` of its `confirmed_at`: an Auto-Approve Engineer has no Notifier and was never asked, so that Transaction was Confirmed a millisecond after the scan, and undoing that mis-scan needed the admin password where every other Engineer's is a pill in the Storekeeper's own window. It is not a way past a confirmation — `auto_approved` is on the row, written when the row was written, so a Transaction an Engineer actually answered is refused whatever the clock says — and it is not a second door around the switch, `storekeeper_can_cancel` being refused before this is asked. The window is decided in `_cancel_transaction`, the one enforcement point, so the endpoint, the Server GUI's ⦸ Cancel Selected and the Storekeeper's Cancel pill are held to one answer, and the `transaction.cancelled` entry says when it was the window that opened it, that being the only place the three doors are told apart afterwards. Since #169 the **Manage Transaction History** capability password over HTTPS opens exactly what the admin password opens here — a Confirmed row, the switch overridden — beside Delete and Correct, which it already opened; the delegate who may delete a row outright and may not retract a Confirmed mis-scan reaches for the deletion, which is the same argument that put `POST /transactions/modify` on the network. It is a credential and not a person, so a `cancelled_by` sent on that path is **ignored** rather than allowed to put a name in front of a delegated act: the column and the `transaction.cancelled` entry both carry `_remote_actor`'s sentence. **Which credential arrived is examined before the transport is judged, and only here** — the admin password is accepted over plain HTTP as it always was, that being the default deployment (rule 1) and the Storekeeper's own path, so a gate on the transport ahead of the password would refuse the ordinary store; the capability password is still refused `insecure` (403) over one, with the same entry and the same words. That is `_remote_admit`'s `admin_is_native` and the one ordering exception ADR-0015 carries. The admin password's use here is **not** a `remote.action` for the same reason it is not gated: it is this endpoint's own credential rather than a remote-channel one, and the `transaction.cancelled` beside it already records the act as the Admin's. **The `cancelled_by` column takes the name alone and the System Log entry takes the role with it** - `<name> (Storekeeper)` where the unauthenticated path was used, since the Storekeeper is its only client, and the caller's own name untouched where it named itself: the same split `_create_transaction` makes, so a cancel and a creation by one person read the same way and a caller that named itself is never dressed as the Storekeeper. **`reason` is capped at `_TXN_TEXT_MAX` and `cancelled_by` at `_TXN_NAME_MAX` (120), both truncated rather than refused and both capped once, at entry** — for the reason `POST /transactions` caps `notes`, and sharper here because this path needs no password at all for a Pending Transaction while the switch is on, so a caller on the network chooses the length of two columns on the one table with no retention bound of either kind. Once at entry because the same `reason` reaches `cancel_reason` and `_log_event`'s `detail` and the same `cancelled_by` decides the `actor` beside it, and one truncation is what keeps the row and the System Log entry saying the same thing. 120 rather than 500 for the name because it is a label and not prose — the class `_CHECKIN_MAX` exists for — and a constant of its own rather than a second caller of that one, the two being facts that happen to share a number. A **blank** reason is still refused: that is a different rule. A body with no `password` key is the unauthenticated path, while `password: ""` is an attempt at a credential and is refused as wrong, not treated as absent — a wrong password never falls back to the unauthenticated path, because that would let a typo silently downgrade an admin and produce a refusal naming the wrong reason. Refused with a `code`: `bad_password` (401), `insecure` (403, a capability password over plain HTTP), `cancel_disabled` (403, the switch is off and no password opened it), `confirmed` (409, already Confirmed and no password opened it), `rejected`, `already_cancelled`, or `not_newest` when it is not the newest non-cancelled Transaction for its asset, naming the id to cancel first |
| POST   | `/transactions/delete` | admin · Manage Transaction History | Body: `{password, ids:[...]}`. The **admin password**, or the **Manage Transaction History** capability password over HTTPS (R1, ADR-0015). Delete one or more records. The `transaction.deleted` entry names which credential asked and, for a capability password, the holder the Admin wrote beside it — the rows are what stops existing, so that entry is the entire record that the act happened, and it said `Admin` whoever had asked for it until R1 |
| POST   | `/transactions/modify` | admin · Manage Transaction History | Body: `{password, id, <any of MODIFIABLE>}`. The **admin password**, or the **Manage Transaction History** capability password over HTTPS (R1, ADR-0015). Any field not sent keeps its value. Refused with a `code`: `no_id` (400), `no_fields` (400), `insecure` (403), `bad_password` (401), plus whatever `_modify_transaction` itself refuses |

| GET    | `/members` | open | List engineers: `[{id, name, auto_approve, profile, permissions, has_password, must_change_password}]`. `id` is beside the name rather than instead of it and every caller still asks by name (ADR-0016): what it is for is a Client that wants to survive the name changing under it, and an Admin window that has to name the row it is renaming.
