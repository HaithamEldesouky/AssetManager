# The rules in full

The one-line form is in [CLAUDE.md](../../CLAUDE.md). Here is each rule with the
reasoning that put it there.

## Strict Project Rules — Never Break These

1. **HTTP or HTTPS on port 8081.** Never `verify=False`. HTTPS requires uploading a certificate via the Server GUI (🌐 Server Settings window). **The clients fail closed:** with no `ssl_cert.pem` next to the app, an `https://` request raises rather than connecting. The branch that used to be there fell back to the system certificate store with `check_hostname` off, which accepts any publicly-trusted certificate for any hostname — one certificate was enough to impersonate the server, and nothing in the system store can vouch for a self-signed one, so there is no safe automatic fallback to have. **What a client with no file may do instead is ask:** on the first `https://` call it fetches `GET /cert` over a connection that verifies nothing, shows the SHA-256 fingerprint of what came back, and writes the file **only if a person accepts it** — trust on first use, with the first use answered by whoever is at the machine, against the fingerprint the Server GUI's Server Settings window shows on the server itself. Nothing but that one GET crosses the unverified connection: no credential, no check-in, no transaction, and every other request still goes through the pinned adapter and still raises with no file on disk. A refusal writes nothing and is not re-asked in that process, and an app that registers no callback — or has nobody watching — refuses rather than pins. **What asks again is the app being started again, and in the installer a click on Install** (`common.reset_cert_prompt`, called from `_install` and from nowhere else): one prompt per process is a rule about a client that **ticks**, since a refusal the poll loop could re-ask would be a dialog every fifteen seconds until somebody accepted it without reading, and the installer asks once per deliberate click instead. Held to the clients' rule it was the installer reporting a server that is up as one it cannot reach: the prompt opens with Cancel as its default button, so a stray keypress refused it, and every later click then failed closed with no file on disk and was answered by `_report_unreachable` — which exists so that a check which could not be made is not reported as a wrong password, and which said here instead that the server was not running, while its one line offering a way out named an offer that could no longer come. Re-arming is the **question** and never the trust: a certificate already on disk is still not re-offered. The installer is still the quiet channel and supplies the file when it has one, so the prompt never appears on an install that was given a certificate. See ADR-0010. Plain HTTP is untouched.
2. **Asset types are driven by the lookup sheet (v1.7.0+).** The valid types are whatever distinct `asset_type` values the Lookup Sheet holds, served via `GET /asset_types`. Since 024 that is the `assets` table rather than `asset_lookup.xlsx`; the workbook is how the list is exported and replaced (ADR-0011). Clients load this list at startup (the Storekeeper's history filter; the form's type is not picked but auto-populated from the sheet's answer) through `common.fetch_asset_types()` (rule 10), which keeps an on-disk cache beside the app: a fetch that succeeds replaces it, one that fails leaves it exactly as it was, so a client shows its last real answer rather than asking again on every window that needs it. Only a client that has never once heard from the server falls back to the baked-in default `Laptop, Desktop, Mobile, Tablet, Screen, UPS, Server, Cisco Phone, Printer, Scanner, Switch`, which lives in `common.py` now rather than in `storekeeper_app.py` alone. Add a new type by uploading a lookup sheet containing it, or by giving an asset that type in the Server GUI's Lookup Sheet window — no rebuild needed either way. (Both doors take the admin password and nothing else writes an asset, so the Lookup Sheet is the trusted source of truth.) **An Asset Model is not a type and is not driven the same way**: `GET /asset_models` serves the models the sheet already holds, narrowed by type, as a list to *offer* rather than a list to be held to - a model nobody has bought before has to be typeable, and filling one in is what rule 6 does for a Transaction that sent none, where a type it corrects.
3. **No "Asset Name" field anywhere.** Asset No. and Serial No. are the only identifiers.
4. **Asset Number and Serial Number are always the FIRST fields in forms and the FIRST data columns in tables.**
5. **At least one of Asset Number or Serial Number is required** to submit a transaction.
6. **Submit validates against the lookup sheet, on the server.** If neither Asset No. nor Serial No. is found in the Lookup Sheet, `POST /transactions` returns 400 with `code: "not_in_lookup"`. If found, asset number, serial number and type are corrected to the sheet's canonical values (handles users who type one correctly but mistype the other), and the model is filled in from the sheet when the caller sent none - never overridden when they did, because that is not one of the three fields this rule corrects. **Every creation goes through one function, `_create_transaction`.** The Server GUI's Add Transaction calls it rather than inserting a row of its own, so this rule cannot hold at the endpoint and quietly not in the window an admin uses - which is exactly where somebody would reach for a way past a sheet that is missing an asset. The only other writer of a Transaction row is the archive importer, restoring rows that were validated when they were first created. The Storekeeper checks the same rule in its form so the user sees it before submitting, but the server is what enforces it — the offline buffer flush, a future client and a curl all go through the same gate. An empty Lookup Sheet skips the check: nothing to check against is not the same as an unknown asset. The refusal still says "not in the lookup sheet" and still carries `not_in_lookup`, because that is what every client and every Storekeeper form already calls it — 024 moved where the assets are kept, not what they are called.
7. **The admin password is changed only from the Server GUI, and is never delegable.** Storekeeper and Notifier apps do NOT have a Change Password feature — only Server. An engineer's **own** password is a separate thing: an admin sets or clears it from the Server GUI's Manage Users window, on that Engineer's own card, and it never affects the admin password. It was set from the Storekeeper's Add Engineer dialog until 013 — that client now creates an Engineer and nothing more, so no password of any kind is set from a client, and since S3 that creation asks for no password either (ADR-0017): **creating** an Engineer is delegated to the Storekeeper by a switch, while **editing** one — the name, the Access Profile, the permissions, the Own Password, deleting the row — stays admin-only. It stayed at the console as well until #171, which gave those acts to the **Server Settings** capability password over HTTPS and nothing else: still not a client's own credential, still never an Engineer's Own Password, and still never the admin password typed into a client — what moved is where an Admin may stand, not who may do it. An Engineer created that way is created with no credential of any kind, which is what keeps the delegation a smaller thing than the door it replaced. A **capability password** is a third thing again, and since ADR-0015 it is not a console credential: it opened one Server GUI action here until Server Administration became one door with the admin password on it, and it is now what an Admin administers this server *remotely* with, which since R1 means three endpoints over HTTPS — and never this one. Changing the admin password takes the admin password and is checked by hand, whatever opened the console around it, because a door that could change the credential it was opened with would be that credential with an extra step (ADR-0015).
8. **Permission names live in one place, and that place is `server.py`.** `PERMISSIONS` is the list and `PERMISSION_LABELS` beside it is what each name is called in front of an admin — a caption, **not a second list**: the Manage Users window loops over `PERMISSIONS` and looks a caption up, so a name with no caption is still offered as itself rather than dropping out of the form. **No client carries a copy.** `storekeeper_app.py` mirrored the list for its Add Engineer checkboxes until 013 moved profile editing to the Server GUI; a client copy is a security-shaped fact written down twice, which is what rule 10 exists to prevent, and `cascade-audit.py` now fails if one comes back. **A client that has to draw the ticks asks for them instead**: `GET /permissions` serves each name with its caption, in `PERMISSIONS`' own order, which is what lets the Notifier's Remote Admin Engineers panel offer an Access Profile (#171) without becoming that second copy — a name with no caption is served as itself, exactly as the console offers it. The server still rejects any name it does not know, so a caller left behind by a change fails at the endpoint naming the offender rather than quietly granting nothing. A permission that gates no real behaviour must not be added, **and must not be kept** — an admin ticks it and believes something changed; that is why 013 deleted `open_settings` once 012 made an Engineer's Own Password open Notifier Settings by itself. `cascade-audit.py` holds the names to the captions in both directions, so neither an uncaptioned name nor a caption for a name that no longer exists can sit there unnoticed. The audit behind what is left — what every sensitive action is gated by, and why nothing else qualifies as a permission — is in `docs/tickets/010-server-rbac-and-sensitive-permissions.md`.
9. **There is NO `/reset` endpoint.** There IS a **Clear All Records** button in the Server GUI — it requires the admin password and a confirmation prompt before permanently deleting all transaction records.
10. **Shared client code lives in `common.py`.** The three client apps import the transport layer rather than each carrying a copy — they used to hold byte-identical copies of the TLS adapter, `api()`, the port cascade and the certificate refresh, which meant a security fix had to be made three times and be right three times. Add to `common.py`, never re-copy. The server stays out of it: it shares no transport code with the clients, and importing a client module into the service would tie the two release paths together for nothing.
11. **`asset_lookup.xlsx` is embedded** as base64 inside `server.py` (`DEFAULT_LOOKUP_B64`). On first run the server extracts it next to the server and **reads it into the `assets` table**, which is where the Lookup Sheet has lived since 024 (ADR-0011); the workbook is the interchange format from then on. To update it at runtime there are **two doors, both admin-password only**: `POST /lookup/upload` replaces every asset with what an uploaded workbook holds, and the Server GUI's **Lookup Sheet** window (reached from the Database Location dialog) adds, corrects or removes one asset at a time. Both go through `_save_asset`, the one writer of an asset, the way every Transaction goes through `_create_transaction` — which is also where **an identifier is held to naming one asset** (025), so the upload door can no longer walk past a rule the window was enforcing on its own. Neither is delegable to a capability password — the sheet is what makes rule 2's asset types and rule 6's refusal trustworthy, so only the admin password changes it. **Answering a proposal is delegable and since #173 is delegated** (`POST /assets/proposals/decide`, the Server Settings capability over HTTPS): approving adds one asset through that same `_save_asset`, in answer to a question the Storekeeper asked, where these two doors replace every asset this server holds — which is the line, and it is a line about the size of the act rather than about which helper runs.
12. **We ship one executable of ours and it is the installer.** The exes are unsigned and every release is a brand-new binary with no reputation, so Defender ASR blocks one of them today. 061 retired `AssetServer.exe`, `StorekeeperApp.exe` and `NotifierApp.exe` altogether: what Windows starts on every machine afterwards is a PSF-signed `python.exe`/`pythonw.exe` with one of our launchers as its argument. `AssetManager_Setup.exe` is the one binary left, because a package has to be openable by somebody who does not have Python yet — it is run once, at install time, and **nothing it copies is an executable of ours**. **The update path is the sharpest case of this, and is why it exists**: a client updates itself by fetching `GET /download/client/<key>`, a zip of `.py` files, launchers and the vendored `lib\`, and `client_update.py` restarts the app through the same signed `pythonw.exe` — no new binary, no reputation to earn, nothing for ASR to block. So: `vendor.ps1` strips every `.exe` `pip` leaves in `lib\` (it writes wrappers like `idna.exe`, and `win32\pythonservice.exe` for pywin32), and `package.ps1` and `bundle-client.ps1` both **refuse to stage any `.exe`** — the installer's own payload included. Do not add one back, and do not "fix" the missing Windows Service verbs by shipping `pythonservice.exe` — IIS is the supported host (ADR-0001) and `server.py` already degrades cleanly behind `HAS_WIN32SVC`.
13. **The vendored `lib\` is tied to one Python minor version.** `pillow` and `charset_normalizer` carry compiled `cp3xx` extensions, so a `lib\` vendored under 3.12 does not run under 3.11. `vendor.ps1` stamps `lib\PYVER` and `applaunch.py` refuses to start on a mismatch, naming the version to install. Never drop that check: the failure it replaces is an `ImportError` deep inside a library, invisible under `pythonw.exe`, leaving the engineer with nothing to report.
14. **Source mode is the only mode, and the engineer-laptop proof is the gate on that.** This rule said the opposite until 061: source mode was additive, `package.ps1 -Build` still produced four exes, and nothing was retired until a real engineer laptop had run a source-mode client. 061 retires the three app exes, so that verification stopped being a precondition for *adding* source mode and became the gate on this change itself. **Do not release a build from here until a source-mode client has been installed and run on a real engineer laptop** — there is no exe path left to fall back to, so what the runbook's "What is not proven yet" lists is now the whole of the ship path rather than one of two. `AssetManager_Setup.exe` stays and is what an engineer is handed (rule 12). IT's answer on signing is still outstanding and no longer blocks what the apps themselves run under, that being Python's own signed binary.
