# The cascade sets, and what each one cost

The short form - which places move together - is the table in
[CLAUDE.md](../../CLAUDE.md). This is the same table with the reasoning kept: every
row below is a copy that drifted at least once, and the sentence after it is the
failure that put the row here.

**Cascade a change to everything that records the same fact.** The blast radius rule above is about *code*: don't touch code the fix doesn't need. This rule is the other half — a fact that is written down in more than one place must move in all of them in the same commit, or the copies start lying. Leaving a stale copy is not "staying in scope", it is shipping a contradiction. The coupled sets in this repo, all of which have bitten:

| change this | and these must move with it |
|---|---|
| `APP_VERSION` | all four sources — `package.ps1` refuses a package when they disagree |
| `PASSWORD_MIN` | `server.py` **and** the copy `installer.py` keeps — that file does not import the server and must not (rule 10), so the number is written down twice and `cascade-audit.py` holds the two equal. The direction that matters is a raise in `server.py` alone: every door there **changes** a password that exists, while the installer's **sets** the first admin password an install ever has, which is what every capability password is measured against |
| a permission name | `PERMISSIONS` in `server.py` **and** its caption in `PERMISSION_LABELS` beside it, plus the count `CONTEXT.md` states in words (rule 8), which is read out of that entry alone — `There is one:` is the glossary's house style, so a search over the whole document answers with whichever entry comes first. No client carries a copy — `cascade-audit.py` fails if one appears |
| the engineer list | `TEAM_MEMBERS` in `common.py` **and** `server.py`'s own seed list |
| a DB column | the migration, `init_db()`'s idempotent `ALTER TABLE`, and the schema block in this file |
| an endpoint's shape | the API table in this file **and** every client that calls it (older clients must still work mid-rollout) |
| a `tools/*.ps1` behaviour | that script's section in the tooling reference **and** the runbook that drives it |
| a capability name or label | `CAPABILITIES` **and** `CAPABILITY_LABELS` in `server.py`, `CAPABILITY_REMOTE` beside them where the new one is reachable over the network, the Capability Passwords bullet in this file, and ADR-0006 with ADR-0015. The label is what the delegate is told their password is for, so the two must not drift — `cascade-audit.py` checks it |
| a new domain term | the glossary in `CONTEXT.md` — and use its wording, not a synonym it says to avoid |
| the Storekeeper's role label or its default name | the label `"%s (Storekeeper)"` is worded once in `server.py` and once in `storekeeper_app.py` and the two must match — the server does not import `common.py` (rule 10), so this is a fact written down twice like `TEAM_MEMBERS`; the default name is `STOREKEEPER_DEFAULT` in `server.py`, the `transactions.storekeeper` column default beside it, `DEFAULT_CFG` in `storekeeper_app.py`, and the Notifier popup's fallback for a row whose column is empty — that fourth is a display fallback rather than a source of truth, and is held to the others anyway, being the same literal and what an Engineer is shown a Transaction came from. `cascade-audit.py` checks both |
| a shared client module | `$Payload` in `tools/bundle-client.ps1` **and** `SOURCE_FILES` in `installer.py`. The two are one set per app — that app's `Source` and `Launcher` plus the shared payload — and `cascade-audit.py` holds them equal. A name in one only is a client that will not start or an installer that refuses its own payload, and neither says so at the time |
| a shipped payload — a file that actually goes into a package | rebuild the affected packages. A manifest's commit must be one whose tree really produced that payload; **a docs-only commit does not invalidate a package**, so don't rebuild on every commit, and re-stamp at release time so what ships points at the released commit |
| a documented measurement or claim | **re-derive it from the source**, never copy it forward from notes or from an earlier draft. A wrong number in a document usually got there by being retyped from memory instead of re-read from where it is actually measured |
| a new module beside an app | the four lists nothing derives and no gate holds: `MAP` in `tools/gate.py`, the two staging lists in `tools/server_checks/stage.py`, and the staging block in `tools/client_checks/stage.py` with the `SRC_FILES` tuple beside it. The three lists a reader expects here are **not** on it, because each is derived now: `$SourceFiles` in `package.ps1` has been held to the module-level import closure of `server.py` and `run_server.py` since 059, `dev-run.ps1`'s staged lists to each app's own closure since before that, and `$Payload`/`SOURCE_FILES` to each other since 063 - `cascade-audit.py` names a module missing from any of the three. Restating them here would train this table to be ignored. What is left is quieter by one step each. `gate.py`'s `MAP` is the mildest and the one that has actually drifted - `server_cert.py` has been absent from it since #206 - and it is fail-safe: a path `MAP` does not recognise runs **every** suite rather than none, so an omission costs a full gate run and no coverage. The two staging lists fail loudly, the suite dying on the module's own import, `STAGE` being first on `sys.path` with the repo root not on it at all. `SRC_FILES` is the one that fails silently: it is the list of files read as *text*, so a module missing from it is simply never swept and the suite goes on passing about less and less - which is the failure its own comment records, a sweep that walked `APPS` alone having stopped reading nine Remote Admin windows and the Export window without saying so |
| a `_log_event` call | that event's row in `docs/system-log-events.md` **and** its phrase in `EVENT_SENTENCES` in `server_log.py` (#196, and in that file rather than `server.py` since #227 made the System Log a module) - `cascade-audit.py` holds the two equal in both directions. This is the one set the repo deliberately does not keep beside its call sites |

When a change lands in a doc that another doc points at, follow the pointer and check the sentence on the other side still holds. Say what you cascaded; if you deliberately left a copy alone, say which and why.
