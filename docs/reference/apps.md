# What each app does

## Key Features per App

### Storekeeper App

- **Whose name it records under is a setting, not a literal.** `storekeeper_name` in `config.json`, defaulting to the `transactions.storekeeper` column default, **set by the Admin in the Server GUI's Manage Users window** and picked up on the 15s tick that already reads `GET /health`. It goes in the `storekeeper` field of every Transaction this app submits — the form, the offline buffer and the bulk flush alike — it is what the header beside the app name says, and the System Log attributes each entry to `<name> (Storekeeper)`. **Absent or empty on the heartbeat is nothing said, not a name cleared**, so a server that predates the key leaves this installation recording under the name it had; the value is written back to `config.json` so `app.started`, logged before the first heartbeat is answered, is attributed to the right person rather than to the default. **The default survives a read**, which is a thing that has to be said because it did not: `load_config` reads the file over a *copy* of `DEFAULT_CFG` rather than into `DEFAULT_CFG` itself, since the second spelling replaces the module's record of what a default is with whatever the file said, and the one line that reaches for it afterwards - `__init__`'s `or DEFAULT_CFG["storekeeper_name"]` - can then never answer with one. A name of spaces in `config.json` left that fallback answering with the spaces: a whole run attributed to `(Storekeeper)` with nobody in front of it, and every Transaction carrying an empty `storekeeper` column, which is the column somebody reaches for when reconstructing a dispute. it is the same function as the Notifier's - both now `common.load_config` - and `server.py` falls back to `STOREKEEPER_DEFAULT`, a constant no loader can reach; this app was the one that put its default somewhere writable. It is **not** editable here and there is no password on it: this is an installation, not a login (see Manage Users).
- **The header band says who this is and nothing else it does not have to** (166). It carried the app name, the Storekeeper's name, the four store counts, the connection pill and the theme toggle on one line, which is a stat strip doing a title bar's job. The four counts are over the **RECENT** list now, which is the surface they are counts of, at no cost in height - that heading was a label and a rule and nothing else - and they are still inline numerals rather than cards for the reason they always were: four tiles cost over a hundred pixels to show four integers, and that height is worth more as rows. `out_now` is still the server's count of what an engineer is holding now, read from `/stats` rather than off the table. **And the version badge is gone from the section bar**: it was drawn into the strip the tabs were packed into and overlapped them, which is what two homes for one fact produces - the version is in the window title, which is where Windows lists it, so the badge was the second copy rather than the first.
- **The window stands on the depth layer** (159): a lit gradient ground behind the whole of it, an accent glow under Submit, a frosted header band carrying the app name and this installation's Storekeeper name, and frosted chrome around the tab strip and around both tables. It is `ui_kit.Surface` and nothing of this file's own, for rule 10's reason - the Server GUI, the Notifier and the installer take the same three behaviours. **The containers that were flat frames became canvases and nothing else moved**: `pack` is untouched, so every window `tools/client-checks.py` measures is measured against the same children in the same places, and nothing here is put on the Tk thread for the 15s background tick to wait behind - one debounced render, and no work at all until the window is resized or the theme switched. **Glass is the chrome and never the surface a form sits on**, which is the rule the prototype settled and which this window is the sharpest case of: a `tk.Entry` and a `ttk.Combobox` cannot be transparent, so the transaction form - both identifiers, the read-only Asset Type, Engineer, Direction and Notes - stays flat CARD, and so do Bulk Scan's panel, the Tools cards and every dialog this window opens. What the glass shows around a table is the ring and the padding, the rows themselves being a ttk Treeview drawn out of its own style - and around the Submit tab's RECENT table there is no ring at all since #179, that column separating things with a groove. The tab rule takes its off-colour from the holder around it rather than from the `BG` literal it held, a palette literal on a tinted strip being a 2px bar of a colour nothing else on the row is. With no `pillow` the window opens as the flat product 157 settled - which here means exactly the window it was before, since each frosted container is drawn in the token it already carried - and `tools/client-checks.py` opens the real window **both ways**, since every machine a release is built on has pillow and a group that only ran with it would report the fallback as passing for ever. What it asserts about the glass is that a panel's colour is the ground beneath it lifted by the tint, read off the backdrop's own render, and about the form that it is flat on both passes.
- **Form:** Asset No. + Serial No. (both first), Asset Type (not a field the storekeeper fills - a read-only display of what the lookup sheet gave, an em dash until an identifier matches), Engineer, Direction, Notes
- **Submit:** Validates against lookup. Rejects unknown assets. Auto-corrects mismatched fields.
- **Bulk Scan Mode:** the **Bulk submit** button beside the Serial no. field (090; a grey text link under the form until then) → floating panel with engineer/direction pre-set → scan barcodes one by one → "Submit All". Each row is answered on its own: one that goes through is one `transaction.submitted`, one the server refuses is one `transaction.refused` and stays in the list to be acted on, and one it never answered goes into the offline buffer and leaves the list (see Offline buffer and System Log below). Rows survive the window being closed and reopened; what they did not survive until #95 was the app being closed. **It is `storekeeper_bulk.py` since #236** - the window and its queue moved out of `storekeeper_app.py` verbatim as `class BulkWindow`, which takes the app and reaches back into it through `bind()` the way `storekeeper_export.py` does; nothing about the window changed.
- **RECENT is a list and the pane beside it** (078). It was a Treeview of seven columns - `RECENT_COLS`, which was `COLS` without Asset Type, the Rejection Reason and Direction (166, #179) on the argument that a receipt says less than the record does and History is one tab away. The trip to History is what 078 removed: RECENT is `ui_kit.ListPane` with `ui_kit.DetailPane` beside it, the shape 076 added and the Server console's Activity feed proved, so the row selects and the pane answers on the tab the movement was submitted on. The **row** is the Asset Number over the Serial Number (rule 4), the direction word and the state right-aligned against them and a 3px direction gutter on the leading edge; the **pane** is the identifier as the hero at 26 with the Asset Type, the model, the Engineer, the Storekeeper the row was recorded under, when it was logged, the note that was typed and a rejection's reason - which is every column that set dropped and the note as well, a note never having been on either table. Under them, what that same asset did before now, read out of the transactions list the 15s tick already holds so it **fetches nothing**, and one action, **Open in history**, which is the door the missing columns used to be: History is where a movement is sorted, searched and cancelled, so the pane names that window rather than carrying a second copy of it. The **selection survives a repaint** - the list is redrawn on every tick, and a pane that emptied itself four times a minute while somebody read it would be worse than the trip it replaced. `RECENT_COLS` is gone with the table, and so is the Treeview margin gutter and `_make_table`'s `cols` and `gutter` arguments; History is the one table left in this window, it states all nine columns, and `_fill_table` still writes **by heading** rather than by position - a positional tuple is how serial numbers come to be listed under Model the day a column moves. `tools/client-checks.py` holds rule 4 against History's columns **and** against RECENT's drawn row, and drives two movements through the pane older-first, so a pane that painted once and never again cannot pass.
- **The Submit tab is two columns, and the identifier is the hero** (#179). The form is a fixed-width column on the left and RECENT - the list and the detail pane beside it since 078 - takes whatever is left, with a 1px groove for each seam; the person at this form is holding a laptop and reading a number off a label, so Asset No. and Serial No. are drawn in the mono face at the largest size in the window and everything else is quieter than them. What the Lookup Sheet resolved - the Asset Type and the model - is a block under them rather than a field, neither being something the storekeeper fills. **Direction is the only colour**, a 3px block beside the picker taking WARNING for Out and SUCCESS for In, which is the same pair the RECENT rows are drawn in; **Submit is the one inverted block**, radius 0, which is what makes it the write action. Under it, **this asset before now**: up to six earlier movements against whatever identifier has resolved, each a direction block, an engineer and a date, read out of `self._all_rows` - the transactions list the 15s tick already keeps current - so it **fetches nothing** and costs no request while somebody is typing. Separated by **grooves rather than frost**, which is not taste: a `tk.Entry` cannot be transparent, so every opaque widget standing on a render has to be handed a *sampled* colour while a 1px groove hands it a known one, and no form in this window stands on a render. Labels are sentence case throughout. **Nothing about what the form does moved** - rule 4, the lookup debounce, the offline buffer and its three answers, Bulk submit, Cancel and every System Log entry are untouched, and the primary control is packed `side="bottom"` **before** the rest, so at the 1180x700 minimum what gets squeezed is the custody strip and never Submit.
- **A RECENT row says the direction and the state, and no longer has to choose** (078, #179). A Treeview colours a row and never a cell, so the axis had to be picked per table: History is searched and is coloured by its **state**, RECENT was glanced at and was coloured by its **direction**, with `OUT`/`IN` in the Treeview's own tree column as a margin gutter and the day band's label and count in the same place. The list row carries both - a 3px direction gutter on the leading edge, the state as a word beside it in the state's own colour - so `_tag_status` is one set of colours again and the `out`/`in` tags are gone with the table. A **Rejected** row's gutter is DANGER rather than a direction, unchanged and for the reason it always was: nothing moved, so there is no direction to state. The day bands went with the Treeview and are History's alone, where they are what a table in timestamp order is read by; RECENT is forty rows of a receipt and a band every few of them is a heading over nothing.
- **Submit, History and Tools are sections on the bar from 076** (078). They were this window's own three labels with a 2px rule under the selected one, which is `ui_kit.SectionBar` written a second time and slightly differently - the same widget the Notifier's tabs and the Server console's seven sections are, rather than a thing that looks like it. The selected cell is `CARD` against the `BG` the strip stands on with the mark on its **bottom** edge, a horizontal strip of abutting cells having no visible leading edge, and the hairline under the strip is part of the widget rather than a rule this window remembers to draw - which is why the bar is packed full width where the tab strip was inset 26px. `_show_tab` swaps the panes and the bar paints itself; it is called from the bar's command and from **Open in history**, and it tells the bar which section it is on, `SectionBar.select` deliberately not firing the callback that would rebuild what it is restoring.
- **A block on the form is a recess, not a tile** (078). The `resolved` block under the two identifiers - the Asset Type and model the Lookup Sheet answered with, which are not fields because neither is something the storekeeper fills - was `CARD2`, one step *lighter* than the card it sits on. It is `INPUT_BG` now, the same fill the two identifier fields above it already carry, so the form reads as one surface with three holes in it rather than two materials; the caption above it and the two lines under it are unchanged, and `v_type` is still the `get()`/`set()` pair `_submit` and the offline buffer read the type out of.
- **History:** Filterable table (Member / Status / Direction / Type), text search, sortable columns. **Auto-refreshes every 15s** in the background (preserving the active filters/search), so confirm/reject status updates without a manual refresh.
- **Cancel:** a **⊘ Cancel** pill in the history header retracts the selected Transaction whose movement never happened, calling `POST /transactions/cancel`. A reason is always asked for and the **admin password** only when the endpoint would demand one — the row is already Confirmed — so the ordinary mis-scan is not slower than the scan that made it, and the caption on that field names which case is asking. **One row at a time**, matching the endpoint's newest-per-asset rule, and a refusal is shown in the server's own words: `not_newest` names the Transaction to cancel first, which a generic failure would throw away. A rejected row is refused before the reason is typed, as a courtesy — the server refuses it too, and that is the check. The offer follows the **`storekeeper_can_cancel`** switch on `GET /health`, which the 15s tick already reads: absent means allowed, so a server built before the switch existed keeps it, an unreachable one keeps the last answer rather than guessing, and the pill is hidden rather than greyed out because the switch is not about the row that was selected and is not something the storekeeper can do anything about. The server enforces it either way — a `cancel_disabled` on click withdraws the offer without waiting for the next tick. **A Confirmed row is not one state where the password is concerned** (#198): `storekeeper_cancel_window_mins` rides the same heartbeat, and a row carrying `auto_approved` whose `confirmed_at` is inside it is offered with no password at all — that Transaction was Confirmed a millisecond after the scan by an Engineer who was never asked. Both facts are read off the row `/export` already sends, and the clock is this machine's against a timestamp the server wrote, so a badly-set client clock can answer either way and costs nothing: the server asks the same question again with its own clock and refuses what it will not take. What is decided here is the form, never the outcome. Absent means **zero** here too, so a server that predates the key offers what it always did.
- **Export to Excel:** Date range + member filter. Produces formatted workbook with summary sheet. **It is `storekeeper_export.py` since #219** — the dialog and `_write_excel` moved out of `storekeeper_app.py` verbatim and reach back into it through `bind()`, the way `notifier_remote.py` reaches into `notifier_app.py`; nothing about the workbook changed, which is what `tools/client-checks.py` writes one and reads it back to say. **The Summary counts the rows the workbook is about**, not a list of engineers: which engineers a set of Transactions was recorded against is a fact those rows already hold, and the per-Engineer table read `TEAM_MEMBERS` instead - the fallback a client shows when it cannot reach the server. One workbook then carried a Detail sheet naming an Engineer added since the build and a Summary eight rows from the Total that did not mention them, three engineers who had done nothing listed at zero, and a per-Engineer column that did not add up to the Total beside it, with the bar chart plotting the same range. Derived rather than listed for the reason a command's status is derived from its two dates and a proposed delivery has no batch column. The **member filter** is a different question, since it chooses before the rows exist, so it is handed `_load_members`' live list the way the form, the history filter and Bulk submit already are - offered the fallback, it meant an Engineer added through this app's own Add New Engineer button could not be picked in the export they were added to appear in.
- **Asset Server Settings:** Admin password required to view/change Server URL — the one field on that window. **A check that could not be made is not a refusal:** `common.verify_admin_password` is a POST, so with the server unreachable the door that guards the Server URL needs the very server a wrong URL is why nobody can reach. Where nothing answered, the window opens anyway carrying `common.offline_url_notice`'s three lines saying no password was checked, takes no grab, and its save writes over the config that is already there rather than a fresh dict, so nothing but the URL moves. A wrong password never opens it: that is an answer, and only an unanswered check opens anything. Which window opens is the app's (`_open_settings`), not the dialog's, and the wording is `common.py`'s so it and the Notifier's Settings say the same thing in the same words (rule 10). Both are logged in 011's idiom — `settings.opened_offline` when the gate opens unchecked, `settings.url_changed` when that window saves.
- **Lookup auto-fill:** Debounced lookup on every keystroke (400ms), through `common.lookup_asset()` (rule 10) - the single-asset `GET /lookup` is never cached, since rule 6 has to be checked against the register as it stands right now. Fills the sibling field and the read-only Asset Type; Clear puts the type back to the em dash.
- **Barcode scanner:** Enter key on either ID field triggers immediate lookup (scanners send Enter after a scan).
- **Engineers from server:** The Engineer dropdown is loaded from `GET /members`. **This app creates an Engineer and does nothing else with one** (013): one **➕ Add New Engineer** button (`POST /members` with a name and an **auto-approve** checkbox, forwarding to `_save_member` like the Server GUI's Manage Users window, so this is a second door to the same rules rather than a second set of them). **It asks for no password since S3** (ADR-0017): creating an Engineer is delegated to the Storekeeper by default, because a Transaction against that Engineer already needs no credential at all (ADR-0002) and the one thing this client could not do was name somebody the list did not hold — a new starter whose laptop is in the store's hands now. The switch is `storekeeper_can_add_engineer`, which has `storekeeper_can_cancel`'s shape and its behaviour: read from disk on every request, absent meaning allowed, toggled at the console with the admin password in both directions, and carried on `GET /health` so the **whole Engineers card is hidden** rather than offering a control the server will refuse — hidden rather than greyed, for the reason the Cancel pill is, and the card rather than the button because what would be left is a heading and a sentence about something that is not there. Three things bound that path and each is a different rule: the switch says whether it is open; a name the list already holds is refused `already_exists`, an update being an **edit**; and a `profile`, a `permissions` list or a `member_password` sent with no password is refused `create_only` rather than ignored, since a field silently dropped is one the caller believes was applied. A body with **no `password` key** is that path, while `password: ""` is an attempt at the admin path and is refused as wrong — `_cancel_transaction`'s convention, so a typo never silently downgrades an Admin. The act is attributed to `<name> (Storekeeper)` like every other act from this client. **Auto-Approve stays with creation** because it is neither a permission nor a credential — it says this Engineer has no Notifier, so nothing will ever be asked to confirm for them — and it is the one fact the person adding the Engineer knows at that moment, standing at the machine where those Transactions are recorded; `_save_member` has no `_KEEP` for it either, so it is sent on every write regardless. **What went, and where:** the **engineer's own password** field and the **Access Profile** choice with its per-permission checkboxes are the Server GUI's Manage Users window, on the Engineer's own card, since a credential somebody can then be that Engineer with, and what an Engineer's own client shows them, are both the admin's decisions and neither could be changed here after the way in; and **🗑 Delete Engineer** went with them, because removing the row takes that Engineer's Own Password down with it. `POST /members` is unchanged — an omitted `member_password` or `permissions` keeps what the row had (`_KEEP`), so this narrower form and an older Storekeeper mid-rollout mean the same thing.
- **Proposing an asset:** an asset the lookup sheet does not hold cannot be transacted (rule 6), and this app is where that is discovered. **＋ Add New Asset** appears on the lookup verdict line at exactly the moment it has said the server will refuse what was typed — and nowhere else on that form, since a standing offer beside an asset that resolved perfectly well is an invitation to propose a duplicate — with the same **＋ Add New Asset** button in the Tools tab for one that is not in front of the form. **The door is named for the job and the answer is not** (S1): the word the Storekeeper reads is Add New Asset, because "propose" describes their position in a workflow rather than what somebody holding new hardware is trying to do — while every sentence about what actually happened goes on saying proposed, since that is what happened, and the popup that reports an asset recorded for an Admin to approve must never read "Added". The wire is untouched: `POST /assets/propose`, `asset_proposals`, `seen_proposals.json` and every `asset.propose*` event keep their names, this being what the Storekeeper calls it rather than what it is. It asks for the two identifiers, an Asset Type and an optional model, which is what an Admin has to approve - the first three required and the Asset Number digits only, which the **server** holds it to (`_asset_shape_error`, 103) and this window shows in the server's words, fitted again to the refusal so a sentence longer than a line is not clipped; the type is an **editable** combobox, because new hardware arrives in a category nobody has bought before and what stops a typo becoming an Asset Type every client offers is that an Admin approves it (rule 2), not that this form would not let it be typed. **Asset Model is the same widget since S2**, which is 026's answer at the console reaching the door actually used by the person holding the hardware: an editable combobox listing the models the register already holds for the Type now picked, re-read when that Type changes, and every model where none is picked yet. It was a bare entry, which is how one laptop came to be held as `ThinkPad T14`, `Thinkpad T14` and `T14`. Editable for the reason Type is, and **not** confirmed with a question the way a new Type is — a Type changes what rule 2 serves every client, a model is filled into a Transaction that sent none and reaches nothing else, so asking would be ceremony. The list comes from `GET /asset_models` through `common.fetch_asset_models` (rule 10: this window and the console's are one query), asked **on the two deliberate moments only** — the window opening, and a Type picked off its list — rather than on every keystroke, a blocking call per keystroke in a window somebody is typing into being a frozen window; every other repaint reads `asset_cache.json`, so offline it offers the last real answer and stays editable. A Type with no model recorded against it offers **nothing** rather than every model in the department, matching the console. **The offline path is a refusal, not a buffer** — a Transaction is buffered because the movement already happened and the record is owed, while a proposal is a question, and a queued question is one the storekeeper believes was asked. The answer comes back on the 15s tick, beside the rejection poll and for the same reason: the Admin has no way to reach this machine except the next time it asks. `seen_proposals.json` beside the app is the same shape as `seen_rejections.json` and is there for the same reason — an answer arrives whenever the Admin gets to it, routinely after this app has been closed and reopened, and a decision shown twice is as bad as one never shown. Only this installation's own proposals are shown, matched on `client_id`
- **Proposing a whole delivery:** twenty machines arrive on a vendor's spreadsheet, so the same Tools card takes an `.xlsx` or a `.csv` (029) behind **📥 Import Asset List**, which is S1's rename of Propose from a file and carries S1's split — the door named for the job, every verdict and every answer still saying proposed. The three stages are the Server GUI's Import Assets in the same order - map the columns, see what every row would become, then send - and **nothing is proposed until all three have passed**. What differs is what the last one writes (proposals, not assets) and that **every judgement is the server's**: this app reads the file, which is the one mechanism an import copies, and `POST /assets/import/preview` answers with the guess, the mapping check and the row verdicts, so the rules a file is held to are one fact and not two (rule 10). The batch is **all or nothing**, which is the endpoint's rule rather than this window's, so a refused row means a file to correct rather than a half-landed delivery - the refused rows are shown beside the good ones and the send is offered only while there are none. The whole file is one `proposed_at`, which is what lets the Admin answer it as one delivery. Offline it refuses rather than queues, for the reason one proposal does, and says so on the window that is already open. Both doors, the one-at-a-time dialog and the file-borne window, are `storekeeper_propose.py` since #237: `class ProposeDialogs`, which takes the app and reaches back into it through `bind()` the way `storekeeper_bulk.py` does; nothing about either changed.
- **Reject notifications, and every other one this app makes, are said on the window** (#193). It polls `/export` every 15s (part of the background tick) and puts a notice on `self.notices` — the strip under the section bar — when an engineer rejects a transaction, and the same `_notice` carries the other two: a proposal an Admin has answered, and a Transaction the offline buffer could not get recorded. Each was `deiconify()` + `lift()` + `-topmost` followed by a modal `messagebox`, and **dropping the forcing on its own would have been worse than leaving it**, which is why this is a replacement rather than a deletion: a `messagebox` is modal and appears over its parent, so a parent behind another application is an app wedged behind a dialog nobody can see. The remedy is the pair. The notice takes no grab and raises nothing, so a Transaction being typed at the moment one arrives is untouched; it waits however long it has to and is dismissed by the ✕ on it; and `ui_kit.flash` asks the **taskbar button** for attention, which is the half that survives this window being behind something else. The strip is bounded at `NOTICE_MAX` (4), oldest given way first, a column with no bound being the same push-the-form-off-the-window failure by another door. It is packed under the section bar and above the section panes rather than inside one, because what a notice carries is about this installation rather than about whichever section happens to be showing. Acknowledged ids persist in `seen_rejections.json` (shows once ever, including rejections that happened while the app was closed).
- **Offline buffer:** If the server is unreachable on submit, the transaction is queued to `pending_buffer.json` and auto-flushed when the server returns — **from Bulk submit as well as from the form**, since the movement already happened either way and the payload that path builds has the same keys in the same shape, so the flush sends it unchanged. Bulk submit held such a row in `self._bulk_queue` alone until #95, a list on the app object that nothing ever writes anywhere, and reported it as *still in the list*: forty assets scanned against a server that is not there were forty movements in RAM, gone with the process, with no file to flush and nothing saying they had ever been owed. The row leaves the queue with them, so a second click cannot send it twice. **A proposal is still refused rather than queued** — it is a question, and a queued question is one the storekeeper believes was asked (ADR-0012). **The flush has three answers, not two.** 201 is recorded and 409 is already recorded by somebody, so both are done with; a connection error, a timeout and a 5xx are the failures this buffer exists for and stay queued; and a **4xx is permanent**, so it leaves the buffer and is shown to the storekeeper in the server's own words, saying the movement is not recorded. Every answer but 201 and 409 used to go back in, which meant a payload the server will always refuse was re-POSTed every fifteen seconds for the life of the installation with nothing ever saying so — and by an ordinary route, not a strange one: the offline path buffers **before** any lookup check, correctly, the Lookup Sheet being on the server, so an asset the sheet does not hold is the likeliest thing to be queued and always refused, which is rule 6's 400 and exactly what the Tools tab's ＋ Propose an asset exists for. Dropping it is also what stops it being shown twice, the answer `seen_rejections.json` gives for a rejection. **A flush that finds the server still down asks it once** — the first transport failure has answered for every row behind it, being the same request to the same host a moment later, so the rest are kept in the order they were queued and the flush stops. The loop runs straight through **on the Tk thread** — the whole background tick is an `after()` callback, unlike the Notifier's, which is a worker — so each attempt is a second this window cannot repaint in: twenty rows against a server that accepts and never answers were twenty five-second timeouts, a hundred seconds of frozen app per fifteen-second tick, in exactly the situation this buffer exists for and a wedged-but-listening server being the state `_port_in_use`'s exclusive bind probe and `threaded=True` are both there to survive. An **answer** that is not 201/409 is not that and does not stop it: a refusal or a 5xx is about one row and the row behind it may well go through. `tools/client-checks.py` holds all three answers, and holds the count of attempts. **The one answer that does stop it is a maintenance hold** (G3, ADR-0018), which is that sentence rather than an exception to it: an ordinary 5xx is the server failing at this one row, where a `maintenance` 503 is the server saying it is taking no writes at all, so it has already answered for every row behind this one exactly as a transport failure has - left to the general 5xx branch, a ten-minute restore would turn a forty-row buffer into forty POSTs on every fifteen-second tick, on the Tk thread, which is the frozen window #99 landed to remove reached through a different door. The **code** is the discriminator and not the status, through `common.held_for_maintenance` (rule 10: a client testing for the wrong string would read a hold as an ordinary error), since a 503 without it is somebody's proxy answering about this request. The **submit** path buffers on it too, for the reason it buffers on a server that is not there: the movement has already happened and the record is owed, and the only difference is that this server said so, which is why the popup carries the server's own words. One `transaction.buffered` entry per hold rather than one per tick - the buffer is doing what it exists for and nothing has been lost, so the fortieth copy adds nothing to the first.

- **Offline buffer:** If the server is unreachable on submit, the transaction is queued to `pending_buffer.json` and auto-flushed when the server returns, and **unreachable is a situation rather than an exception class**: a server that never accepted the connection and one that accepted and then went quiet are the same thing to somebody standing at the store with an asset in their hand. `_submit` decided it from the class and named `requests.exceptions.ConnectionError`, which `ReadTimeout` is not - `ConnectTimeout` is one, inheriting from both, and `ReadTimeout` sits outside it - so the one server state this system is built to survive, the wedged-but-listening one that `_port_in_use`'s exclusive bind probe and `threaded=True` both exist for, was the one that refused the Transaction rather than buffering it. The lookup leg is a `GET` that writes nothing, so a timeout on it says only that the server could not be reached, which is what `_check_server` and `_flush_buffer` already call offline. The **submit** leg is deliberately not widened: a timeout there leaves the write's outcome unknown, and the duplicate-pending guard only absorbs a resend while the row is still pending. `tools/client-checks.py` holds both spellings to the one answer.
- **Check-in:** the 15s background tick also `POST`s `/clients/checkin`, so this installation appears in the Server GUI's Connected Clients list with no configured Engineer (it has none) and collects whatever the Admin queued for it. **Log Off** closes the window, deferred by one Tk callback so the tick it arrived on finishes and re-arms first; it is last in the tick, after the offline buffer has had its chance to flush, because a log-off must not be what strands a submission waiting for the server to come back. **Reset Identity** clears the identifier and nothing else — there is no setup wizard here to run again. **Apply the published update** (#177) is the same `_apply_source_update` the 🔄 Check for Updates button calls, with nobody asked: it reads `GET /version` for itself, does nothing where this installation is already on the published version or where this server holds no package for it, and says which of the two in the `command.obeyed` line it writes. **Trust the staged certificate** is `common.trust_next_cert` and nothing of this app's (rule 10); what is this app's is the `cert.trusted` line it writes where one was actually appended, and that nothing is shown — a certificate the server has bound nothing to is not a thing to interrupt somebody mid-scan about.
- **System Log:** every action this app takes is written to a rolling `client.log` beside it **and** shipped to the server — both, because the server's copy is the one the Admin reads and the only place all three components sit on one timeline, while the local file is what this machine can still say about itself when the server cannot be reached. The shipping loop and the rolling file are `common.py`'s, one copy for all three clients (rule 10); *what* is logged is this app's own decision. Here that is the app starting and stopping, a Transaction submitted, one the server refused, one buffered offline, each Client command obeyed, and **the whole of an update's lifecycle** (#148): `update.offered` when a newer version is published, `update.declined` on a postponement, `update.download_failed` and `update.verify_refused` at `warn` for the two ways an update stops before anything is replaced, and `update.staged` - which was `app.update` until #148, the same act renamed into the lifecycle the rest of them are written in - as the last thing this process says before the applier takes over. What became of it is `update.applied`, `update.failed` or `update.rolled_back`, and those are not this app's to word: phase two cannot log at all, so it leaves `update_result.json` and `common.report_update_result` writes the entry on the next start, asked for here immediately after `app.started` so the two entries that bracket an update sit together on the Admin's timeline. The three names, the file and the wording are `common.py`'s because both clients state them (rule 10). **Each of the first three belongs to the Transaction rather than to the form it was typed into**, so Bulk submit writes the same two entries the single-asset form does, in the same wording and at the same levels - one per Transaction, because `_create_transaction` writes a row per asset and a batch is not a thing the `transactions` table has to attribute a summary line to. `_bulk_submit_all` wrote none at all until #100, which meant twenty assets scanned in one sitting were twenty rows on the server and nothing in either half of this log, while the same twenty typed one at a time were twenty entries in each - so the path that carries the volume was the invisible one, and the log read as though this store only ever submits one asset at a time. The refusals are the half that cost an Admin something concrete: a bulk row the server turned down is a message box that is dismissed and gone, and `transaction.refused` is the only durable record that it was attempted. A **409** is the one answer neither path logs - it says somebody has already recorded this movement, which is the same answer the offline buffer's flush treats as done. **The buffered one belongs to the buffering rather than to whoever asked for it.** It was written by `_submit`'s two offline legs and only one of them had it, and the one that did was the narrow race - the server falling over inside the few hundred milliseconds between the lookup and the submit. A Transaction queued because the server had *already* stopped answering, which is the whole situation the offline buffer exists for, was recorded nowhere: not in the queue the Admin reads, and not in the `client.log` that exists precisely so this machine can say what it did when the server could not be reached. So it is written in `_buffer_add`, the one place a Transaction is added to that queue, the way `_create_transaction` and `_save_asset` are the one writer on the server - a third caller cannot appear without it, and the wording is one copy rather than one per leg. `tools/client-checks.py` holds both legs to the same entry. **Every one of them is attributed** — `<name> (Storekeeper)`, from `sk_actor()` — rather than only the Transaction, which was the one entry carrying an actor before: an entry with an empty actor is the Admin reading the System Log and not being told who did it, and the whole point of a name is that the answer is not always the same person. The role in brackets is a log label and never the `storekeeper` field of a Transaction, which carries the name alone. The file is bounded at 256 KB with one generation kept, so this machine spends at most twice that however long it runs. The queue rides the 15s background tick, **before** the check-in: a Log Off collected there closes the window, and what has already been written should have had its chance to reach the server first. A batch the server *answered* is dropped whichever answer it gave — a refusal retried is the same refusal — and only an unanswered one is kept, bounded at 200 entries with the oldest giving way. The local copy is never trusted to match the server's.
- **Update check (v1.6.0):** On launch, polls `GET /version`; if the server advertises a newer build than the app's `APP_VERSION`, prompts the user. **Two answers behind one Yes, and the question says which.** Where `/version`'s `client_packages` carries this app's zip, Yes applies it in place through `client_update` — the download and every check run on a worker while the 15s tick goes on flushing the offline buffer, and the window is closed only once a verified package is staged, because closing it is what releases the applier waiting on this process id. Where it does not — an older server, or a machine with no bundles beside it — Yes opens `/download/installer` in the browser exactly as it did. **A server holding neither is answered once, and only when asked**: `GET /version` advertises the running server's own `APP_VERSION` whatever else it holds, so a server updated ahead of the bundles beside it tells every older client it is behind and offers it nothing — which on a launch check is a dialog nobody in front of it can act on, shown again on every launch for as long as the bundles are missing, with an `update.offered` beside it recording an offer that was not one. So the launch check says nothing and writes nothing on that branch and the manual check still answers it, an installation that is behind staying visible to the Admin exactly where it already was, in Connected Clients. `tools/client-checks.py` holds both apps to it, and to the offer that **is** real still being made. Defender-safe both ways: no executable of ours is fetched by the app, and nothing runs until the user has answered. A refusal is shown in the updater's own words and leaves the app running. The user may postpone **5 times** (counter persisted per pending version in `update_state.json`); the 6th launch shows a non-dismissable "Update Required" dialog that installs or downloads — whichever of the two this server offers — then closes the app. The current version is shown in the window title, and a manual **🔄 Check for Updates** button sits in the history header.
- **Appearance:** a sun/moon button in the window header cycles Dark, Light and Follow Windows, saved as `theme` in `config.json` and applied to the open window - the filters, the search text and the selection all survive it. All three modes stay on the one button: `system` is a real value in `config.json` that the Notifier and the Server GUI both offer, so dropping it in this app alone would leave one app's config disagreeing with the other two. The icon is the theme in force and the caption is the mode behind it, which is what keeps a "Follow Windows" that has resolved to dark readable as something other than a plain "Dark". Asks for no password: it changes what this screen looks like and nothing else. "Follow Windows" is polled on the 15s background tick, since Windows raises no event for it.
- **Tray icon and hide-on-close** (#272): a tray icon built by `ui_kit.run_tray_icon`, the helper #271 put there for all three trays. Its menu, top to bottom: `Storekeeper - <name>` and `Version <APP_VERSION>` as disabled captions, then **Show console** (brings the window back), **Check for updates** (the Tools tab's button's own callback, one path), and **Exit**. Closing the window hides it to the tray; only Exit quits, and quitting still logs `app.stopped` and ships the log as before. Where pillow or pystray is missing (`HAS_TRAY` false) there is no tray, and closing the window quits as it always did.

The protocol on it is the banner's `_ssl_active`, decided when the listener was bound: the tray re-read the certificate files each tick and so called itself HTTPS the moment one was uploaded, a restart before the listener was. **And since #176 `_ssl_active` asks who is terminating TLS rather than what this install's own files say** — `_iis_tls_bound()`, else `ssl_enabled` with both pem files beside the server, which is exactly the expression it was off IIS. `install-iis.ps1` never writes `ssl_enabled` and leaves no key on the machine at all under `-PfxPath`, so the old expression read false on every IIS install: the banner and the tray said HTTP over an HTTPS site, and the five-second liveness probe behind them fired `http://127.0.0.1:443/stats` at a TLS listener, failed, and captioned a healthy server **NOT RESPONDING**. The server already answered this correctly one function over, `_remote_tls_ok` reading that same thumbprint; the banner and the probe simply did not ask it. **And once the scheme was right the transport was not** (#280): the probe handed a `CERT_NONE` context to a `requests` HTTPAdapter, and requests 2.32 puts `cert_reqs=CERT_REQUIRED` back over it on every request, so a self-signed IIS site still read NOT RESPONDING. Both loopback probes - this one's `/stats` and Server Settings' `/health` read for `port_locked` - now make their HTTPS request through one `_loopback_get` in `server_gui.py`, over `http.client` with that same context; plain HTTP is unchanged. **That thumbprint is only half the answer and #185 is the other half**: `install-iis.ps1` is its one writer, so a certificate bound any other way leaves it empty over a live https site and all four surfaces read HTTP again - `_iis_tls_bound` asks the port for a handshake where the record says nothing, so what these three now rest on is what the box is doing rather than only what this install did. The probe reads `_ssl_active` now rather than re-deciding the protocol off the certificate files every tick — one answer, on the surface that already carries it. **And having got the scheme right it then refused the handshake, which is #186**: it pinned `ssl_cert.pem` as its own trust anchor under `CERT_REQUIRED`, which is right only where this process bound the listener — the certificate an IIS site presents is whatever was bound to it, a pfx imported by thumbprint or a certificate picked in IIS Manager, and under `-PfxPath` that file is not on the machine at all, so the `exists()` guard skipped the anchor and left `CERT_REQUIRED` against an empty store, refusing every certificate there is. Either way a healthy server was captioned **NOT RESPONDING** again, one step further along than #176. It verifies nothing now, and the argument is `_port_serves_tls`' own one table up rather than a second one: this is loopback to `127.0.0.1`, the request is `GET /stats`, which carries no credential and needs none, and what comes back is four integers on a window on this same machine — a server asking what its own port is doing, not a client deciding whether to trust a server. - **"Capability Passwords"** — an entry in Server Administration. That door is the second to use `_remote_admit`'s `admin_is_native` after `POST /transactions/cancel`: the admin password is those endpoints' own credential and stays accepted over plain HTTP, the capability password beside it is still HTTPS-only. **The second of the four is Mail Settings** (#172) - `GET`/`POST /admin/mail`, `POST /admin/mail/test` and `GET`/`POST /admin/notify_rules`, all five through one `_mail_door`, which is `_remote_authorise` rather than `_member_door`'s `admin_is_native`: these five routes are **new**, so no shipped client sends the admin password to any of them and there is no install to break by holding both credentials to HTTPS. What that widens is a setting and never a secret that can be read back - the SMTP password may be set over this channel and is answered by none of the five, since it is the one password this server holds rather than checks (ADR-0013). **The third of the four is Asset Proposals** (#173) - one route, `POST /assets/proposals/decide`, which calls `_remote_authorise` directly rather than growing a `_proposal_door`: a named door exists where several routes ask one question, and a helper wrapping a single call site would be a byte-identical copy of `_mail_door` (rule 10), which is why `POST /records/import` and `POST /admin/server_config` have none either. It is the largest of the four by blast radius and the smallest by surface: approving writes the register, so this password can add an asset that can then be transacted and a type every client afterwards offers - while **replacing** the sheet stays the admin password and nothing else (rule 11). **The fourth and last of the four is the Client registry** (#174) - `GET /clients`, `POST /clients/command` and `POST /clients/push_cert`, each calling `_remote_authorise` directly for Asset Proposals' reason: three routes asking one question with no decision of their own to keep in one place is a `_client_door` that would be a byte-identical copy of `_mail_door`. What moved with it is the shape `_modify_transaction` settled at R1 - `_queue_command` and `_push_next_cert` checked the admin password **inside** themselves while the console was their only caller, and a helper holding a password could only ever know about one of two doors, so each takes an **actor** now and the console asks for the password itself. With this the capability covers all four areas it was named for; a panel added after it is a new capability rather than a fifth area of this one. **`CAPABILITY_REMOTE` is written as the set that *is* remote rather than the one that is not**, for `MAINTENANCE_OPEN`'s reason — a capability added later defaults to console-only rather than to the network — and **SSL Certificate is not in it and must not be**: installing a certificate means uploading `ssl_key.pem`, the one file that must never travel (rule 1), so that one stays a console action and the window says as much on its own row. **HTTPS only** — a capability password is the one credential here that is *replayed* rather than compared against a hash, so a plain `http://` request carrying one is refused `insecure` (403) **before the password is examined**, which is a different answer from `bad_password` because the credential was not the problem. Under IIS the hop into this process is loopback HTTP, TLS having ended at the site, so `_iis_tls_bound` is the second signal and the one that makes the feature reachable on the supported deployment at all; since #185 an `iis.json` naming no thumbprint is not a refusal on its own, the port being asked for a handshake before this door is shut - that record has one writer and a certificate bound any other way leaves it empty over a site that is serving https, which is why every Remote Admin panel was refused `insecure` on exactly those installs. Every change here takes the **admin password**, checked directly rather than through `_authorise`, so a capability password can never grant or revoke itself. A capability password opens only its own action; the admin password keeps opening all five, so a delegation can never lock the Admin out. Minimum 4 characters, and the admin password itself is refused — it would look like a delegation while handing over everything. Whether one is set is derived from the map each time it is read, never stored as a flag beside it. **The holder is a label on the credential, not an authentication of a person**: it is what the Admin wrote down about who they handed the password to, it is set with the password and cleared with it (a name beside no credential names nothing), and an unset one is the state "unnamed" rather than a fallback to `Admin`. It is **copied into each row at write time, never joined to later**, the rule `_rename_member` keeps for `system_log`: a password is rotated by replacing it and the name beside it changes, so a join would re-attribute every past act to whoever holds the credential today. **The System Log says which of the two passwords opened the action** — `_authorise` answers with the credential rather than a bare bool, `_console_actor` turns that into the `actor` column at the console (`Delegate: <label> (Server GUI)` / `Admin (Server GUI)`) and `_remote_actor` does the same over the wire (`Delegate: <label> held by "<name>" (remote)`, `Delegate: <label>, unnamed holder (remote)`, or `Admin (remote)`) — capability first and holder second, with the `Delegate: ` prefix kept on all of them so a filter over it goes on matching. Every row still goes through `_queue_command`, so its duplicate guard refuses a second command while the first is waiting and allows a re-push once it has been collected, which is what a second rotation needs and is safe because the append is idempotent. `_push_next_cert` — which since #174 takes an actor rather than a password, for the reason `_queue_command` above does, and which `POST /clients/push_cert` forwards to — refuses outright where nothing is staged, since a queue of commands that each answer "nothing staged" is a fleet of collected rows meaning nothing happened, and it writes one `cert.pushed` per Client naming the fingerprint — which is what that entry adds over the `client.command_issued` beside it, a command name alone being unable to say months later which certificate it was about. All four commands are obeyed by the Client on its next check-in — `logoff` closes the app down through its own quit path, `reset_identity` throws the identifier away so the next check-in registers a new installation, `trust_cert` appends, and `update_now` applies the published release and the app restarts itself. None of them ends the Windows session: that is not this system's to end, and `COMMAND_LABELS` says so. **And it is where the list itself is tidied up** (#203, #268): **⌦ Clear Old** removes every installation not heard from for longer than a threshold the Admin types as `days:hours:minutes` — `1:12:0` is a day and a half — into a field that replaced the four fixed choices #203 shipped, taking the **admin password** and a confirmation naming the count, since the delete is not reversible and those rows are the only record those machines existed. An **age** and never a selected row, which is `⇪ Push Certificate`'s argument in reverse: nothing here holds a connection, a Client is on this list because it checked in, so how long ago is the only question the list answers and a per-row delete would be an Admin removing whichever row looked stale — a laptop that has been off for a fortnight looks exactly like a machine that was reimaged. The count in front of the Admin and the rows that go are one `_stale_clients`, so the sentence somebody confirms is the delete they get; a row whose `last_seen` cannot be read is **kept**, a timestamp nothing can measure being a reason to leave a row alone rather than to treat it as infinitely old; and `CLEAR_AGE_MIN_DAYS` (1, dropped from a week at #268 now that a field can name a threshold finer than a day) is the floor, a threshold of nothing at all being a fleet reset rather than housekeeping. It calls `_clear_stale_clients`, which takes an **actor** and no password for the reason `_queue_command` above does, and `POST /clients/clear` forwards to that same helper. **The `client_commands` rows are kept**, orphaned on purpose: an uncollected command is the evidence that machine was not running and the `client.command_issued` beside it records an Admin reaching into somebody's machine — `transaction.deleted`'s argument one table over — and since the Client keeps the identifier it generated once, an installation that is still running reappears under the same `client_id` and is still handed whatever is still waiting for it. So this is housekeeping on a list and **not** a way to withdraw a queued command, which the window says on its face. One `clients.cleared` entry at `warn` naming the count, the threshold and how many are left, written even where nothing matched. **The threshold typed here is also saved**, to `clear_age_threshold_days` in `server_config.json`, because #268 gave this the same number a background job now runs on: `_client_sweep_loop`, started from `_start_background_jobs` beside the sync and log-retention loops, wakes hourly, re-reads that saved threshold and calls the same `_clear_stale_clients` as `Auto-clear` — but only writes the `clients.cleared` entry where it actually removed a row, since a job ticking every hour logging "0 removed" the other fifty-nine times would flood the System Log with the same nothing. ### Background jobs (server)

- **Auto-accept:** transactions left pending for **more than 24h** are auto-confirmed (hourly check).
- **System Log retention:** hourly too, on a loop of its own rather than folded into the Auto-Accept one — that job is named for the rule it applies, and a second rule hiding inside it is how one of them comes to be removed with the other. It drops entries older than `LOG_RETENTION_DAYS` (90) and anything beyond `LOG_MAX_ROWS` (50000). Two bounds because `POST /clients/log` is unauthenticated: an age bound alone cannot bound a table anybody on the network can write to as fast as they like. **Neither bound is reachable by hand** — an Admin who wants the log off this machine sooner than a quarter, or a compromised window of it gone now, has the System Log pane's own **Clear** for that (ticket A9): the admin password, a confirmation naming the count, and `log.cleared` written after the delete as the only evidence it happened. **The clients' own retention is the rolling file's size bound**, not an age — a laptop that is off for a month must not come back to an empty log, and 256 KB with one generation kept is a bound it cannot exceed either way.
- **Auto-approve members:** engineers flagged `auto_approve` have no Notifier — their transactions are confirmed instantly (never pending).
- **Auto-accept and auto-approve are different mechanisms** — one letter apart, easy to conflate. Auto-accept is a 24h deadline that applies to every engineer; auto-approve is a per-engineer flag that skips verification entirely. Changing one never changes the other.
- **Asset Sync:** a loop of its own, waking every minute and running when `sync_interval_mins` has elapsed since the last run, **whoever started it** — every run stamps that clock itself, under the lock that already decides whether it is a run at all, so the console's Run now is one of them and the loop's own line is the boot seed and nothing else. What the interval spaces out is reads of somebody else's API, and a Run now a minute before it elapsed used to be answered by a scheduled run a minute later — a second fetch of the same list, which is the thing the wait after a boot exists to avoid. The interval is re-read from `server_config.json` on every tick, so an Admin who has to stop a sync does not have to restart the server to do it, and `0` means no scheduled run at all while the console's Run now still works. One run at a time, a failure is a `sync.failed` entry rather than a raise, and it never deletes (ADR-0014).
- **Concurrency (v1.6.0):** the Flask server runs `app.run(threaded=True)` so multiple Notifiers + the Storekeeper are served on their own threads. Without it the dev server is single-threaded, and one stuck/slow keep-alive connection (a sleeping client, a brief DB lock) blocks **all** clients until `AssetServer.exe` is restarted — the process stays "running" but unreachable. Per-request SQLite connections are isolated, so threading is safe. (For heavier load, a production WSGI server like waitress would be the next step.)
- **Single-instance detection (v1.7.0):** the GUI decides monitor-vs-serve with `_port_in_use(PORT)`, which uses an exclusive **bind** probe (`SO_EXCLUSIVEADDRUSE`, binds then immediately closes — it never serves) instead of a 1s connect probe. A connect probe returns "free" when the running server is listening-but-wedged/slow, which previously let the GUI start a **second** Flask; with Windows' `SO_REUSEADDR` (Werkzeug's default) both then bind port 8081, split client connections, and wedge the server. The bind probe instead reports "in use" for a wedged-but-listening server (GUI stays monitor-only), while still reading "free" when the listener is genuinely dead (GUI can self-heal by starting Flask). The **live listener keeps `SO_REUSEADDR`** on purpose — an exclusive live bind cannot rebind over `TIME_WAIT` client connections and turns a routine restart into an outage, so duplicate protection lives only in the detection layer, never in the live bind. What monitor mode **shows** is no longer identical to what a serving window shows: where `iis.json` sits beside the exe the banner names IIS and the app pool, so the window that is not serving stops looking like the one that is. The probe itself is untouched - that file says who owns the process, never whether the port is busy. **The tray carries the same fact while the window is hidden** - the icon's status dot is rebuilt by `set_health` from the same `online` read that colours the banner and words the tooltip, through `_make_server_tray_icon(online)`, so an operator who has minimised the window is not left restoring it just to learn whether the port is being served.

A **reinstall keeps the rest of that file and changes `port` alone**, a read-modify-write for the reason `_save_server_cfg` read-modify-writes, and an existing file it cannot read is left untouched with the popup saying the port was not applied — which is the same pair of answers `_write_admin_cfg` gives about `admin_config.json` beside it, since two doors in one function answering one question two ways is how the first of them came to be wrong. The field is prefilled from whatever install sits in the directory it is pointed at — following the directory, including one chosen through Browse — so a reinstall does not quietly move a server off the port it was serving on. It governs the Windows Service and the standalone GUI: under IIS the real binding is the site's and `tools/install-iis.ps1` is what writes the port, which is what the field's caption says without claiming otherwise. **Registering that Service runs the launcher and not the target alone**, which is the shortcut defect below one call further down and quieter: it ran `[dst, "install"]`, and in source mode — the only mode (rule 14) — `dst` is `pythonw.exe`, so what ran was an interpreter with no script. That exits 0 having registered nothing, `net start AssetManagerServer` then fails against a service that was never created, and the command printed underneath as the manual remedy was the same one written out by hand — so following it did the same nothing. `_service_command` builds the argv and that sentence together, because they are one command and a remedy that is not what actually ran is worse than none; `tools/client-checks.py` drives both modes over it and holds the install to asking it rather than keeping a second spelling. **IIS is still the supported host** (ADR-0001) and `server.py` degrades cleanly behind `HAS_WIN32SVC`, so what this fixes is the command being right — nothing here ships `pythonservice.exe`, which rule 12 forbids.
- **Storekeeper install:** prompts for Server URL and the **admin password**, verified live against the server before anything is written. It asked for the URL alone until ADR-0007 — anybody with the package could stand one up and point it at the store's server. It is a control over who installs one, not a network boundary: `POST /transactions` is unauthenticated on purpose (ADR-0002), so this stops nobody from doing what a Storekeeper does. It supplies `ssl_cert.pem` when it has one, from a copy placed beside `AssetManager_Setup.exe` — nothing is built in since 061 — but no longer has to: an install with no certificate offers the server's fingerprint for confirmation on first contact instead of dead-ending (ADR-0010).
- **Which Python a source install runs under is resolved from `lib\PYVER`, not from the interpreter that opened the installer.** The vendored `lib\` runs under one Python minor version and no other (rule 13), and what opened the installer is whatever the `.pyw` association points at — on a machine carrying two Pythons that is the newest one, which is how a laptop with 3.12 and 3.14 installed a 3.12 bundle and then met applaunch's refusal on the first click. So `_gui_python` takes the running interpreter only when it already matches, else asks the `py` launcher for `-<version>`, and where neither answers the install is **refused before a single file is copied** — naming the version to install, rather than succeeding into an app that can never start. It is the shortcut that makes this stick: the launcher opened on its own goes back through the association. **A `lib\` with no stamp on it was the hole in that**, and a state every other reader tolerates: `_payload_mode` asks only that `lib\` is a directory, `applaunch.py` skips its own check where there is nothing to compare against, and `_ensure_python` reads a missing stamp as the pinned series. `_gui_python` read it as “the interpreter I am running under will do” — the frozen guard was in the second half of that condition only — and under `AssetManager_Setup.exe` that interpreter is the installer, so the Desktop shortcut named Setup and reopened it on every click, with `applaunch` never reached to say anything about it. It asks the machine for `PYTHON_SERIES` instead, which is the same answer `_ensure_python` gave the same question minutes earlier, and `PythonMismatch` names that series rather than `None`. `tools/client-checks.py` holds it.
- **Notifier install:** prompts for Server URL, engineer name, and a password — the Engineer's own **Own Password**, or the admin password, verified live before install proceeds and checked against **the Engineer this install is being configured as**. Accepting any Engineer's Own Password for any name would let one install a Notifier configured as another and then confirm or reject that person's Transactions. It goes through `common.py`'s `verify_password`, so the fallback for a server without `/auth/verify` is not copied in here (rule 10). Demanding the admin password meant an Engineer could not install their own client without being handed the password that also opens Clear All Records — see ADR-0007. The engineer dropdown loads from `GET /members` (with a ↻ refresh button; falls back to `TEAM_MEMBERS` if the server is unreachable), so newly-added engineers are selectable without rebuilding the installer. It supplies `ssl_cert.pem` when it has one, and where it has none the Notifier asks the engineer to confirm the fingerprint on first contact rather than refusing every request (ADR-0010) — the live password check above runs over that same first connection, so on a certificate-less install the engineer is asked to accept the fingerprint before they are asked for their password. **A refusal there costs that click and not the installer**: every Install re-arms the prompt (rule 1), because this is somebody asking on purpose rather than a poll loop, and the dialog's default button is Cancel. Writes `poll_interval: 15`.
- **Both client installs put Python 3.12 on the machine first** if it is not already there - `_ensure_python`, after the password check (so a wrong password is not answered with a several-minute install) and before the payload is copied. It arrives three ways, in order: `python-3.12.*-amd64.exe` beside `AssetManager_Setup.exe`, then a copy embedded at build time, then a download of the pinned `python-3.12.10-amd64.exe` from python.org - 3.12.10 because it is the **last 3.12 with a Windows installer**, the series having gone security-only and source-only after it. The middle one is a fallback nothing fills: `package.ps1` refuses to stage any `.exe` at all (rule 12), so **nothing here embeds one** and in practice it is the loose file or the download, and an admin shipping a newer patch drops it beside the installer rather than rebuilding. It was described here as `_ssl_cert_source()`'s shape until #155, which took that one's dead half out: a fallback with no source makes one question look like two, and the two readers of *is there a certificate to install* had already drifted apart on it. Whatever it is about to run is checked for a valid **Authenticode signature from the Python Software Foundation** rather than against a pinned SHA-256: the file arrives three ways and a hash pinned to one patch release would refuse the other two, while the signature is the same thing rule 12 rests on. Installed all-users (`InstallAllUsers=1 PrependPath=1`), silently, with a progress bar as the only thing on screen - the installer is already `--uac-admin`, and a laptop a second engineer signs into must not lose the interpreter with the profile. **`Include_tcltk=1` is stated rather than inherited**: it is the python.org installer's default, but a default is remembered from the last install on that machine and is a tickbox anybody can clear, which is not a guarantee - and three of the four apps here are a Tk window and nothing else, so an interpreter without it installs cleanly, reports success and can never open anything. That is a whole install with no window on it, and until `applaunch._die` stopped drawing its own box with tkinter there was no message either. `tools/client-checks.py` holds the flag beside the other four, a rewrite that adds this one and drops `InstallAllUsers` being the laptop that loses its interpreter with the first profile deleted. **It is not a gate:** a failure warns and the install continues, since `installer.py` still reads an exe payload where the client carries its own interpreter (`_payload_mode`), and the refusal that actually stops a source install is `_deploy_component`'s `PythonMismatch`, raised when no Python matching `lib\PYVER` is on the machine - running first is what gives that refusal something to find. It asks `_python_installed`, the one probe `_gui_python` also asks, and stands aside when `lib\PYVER` names a minor other than the pinned one, since installing 3.12 would not answer that question. **What it downloaded, it removes**, and only that: a copy dropped beside `AssetManager_Setup.exe` is the admin's and is left where it was, while the fetched one is 25 MB under a `mkdtemp` name nothing will look for again - sharpest on the refusal above, a file that failed the Authenticode check being the last thing to leave sitting on a laptop named as Python's own installer; the delete ignores its own errors, for the reason this whole step warns rather than gates. And **its own failure is reported like any other**: the call sits inside the `try` each client install reports from, because what runs here is a render loop on the Tk thread for as long as the Windows installer takes and a `TclError` out of it escapes to Tk's handler - a console that is not there under a windowed exe - which left an installer that had stopped, an empty error label and nothing anywhere saying why. Being inside that `try` is not what would make it a gate: the warn-and-carry-on is in its own reporting.
- All three show success popup and auto-close on success. **Every popup says how to start what was installed, and says which of the two ways it is.** The server's is a sentence of its own (`_console_note`) rather than the clients' one reworded: `_launch_note` says the app does not start on its own, which is the opposite of what a server does — the Service and IIS both start it with nobody there — and what that shortcut opens is the **Server GUI**, which is the console. Server Administration, Mail Settings, Backup / Restore, the Lookup Sheet, Asset Proposals and Connected Clients are reached from nowhere else, and under IIS it is the only way in at all, the process that is actually serving being an app pool worker in session 0 with no window and no tray. The server install wrote its shortcut with the **target alone** until this was found, dropping the launcher the payload named, so in source mode — the only mode (rule 14) — it pointed at a bare `pythonw.exe`, started an interpreter with no script and exited without drawing anything: an install with no console, and nothing saying so, since the `.lnk` is written and cscript reports success. Both client installs already passed all three, which is why it went unseen. `tools/client-checks.py` holds every `_create_shortcut` call site in that file to carrying the argument, and holds this popup to saying how to open the console either way. **An update does not write one**: `tools/update.ps1` writes what a package manifest names and nothing else, it never runs `installer.py`, and no shortcut is in any manifest — so a server updated in place keeps whatever shortcut its install left, and an IIS host that never had one gets one by running `AssetManager_Setup.exe` again or by the command that popup prints. The entry point is a Desktop shortcut and in source mode its target is a signed `pythonw.exe` with the launcher as its argument (rule 12) — there is no exe of ours to double-click, by design. That argument is a quoted path, and pasting one into the shortcut helper's VBScript unescaped closed the string early and failed the whole script to compile, so **source mode never once created a shortcut** while the window went on saying it had; exe mode passes no argument, which is why it never showed. So every value is escaped now, the Desktop comes from WSH rather than `%USERPROFILE%` (a domain machine redirects it to OneDrive or a home share often enough that the literal path is a directory that is not there), the helper returns whether a `.lnk` is actually on disk, and where it is not the popup prints the command to start the app with instead of a sentence about a shortcut nobody has. A shortcut is still a convenience and its absence is still not an install failure — but it is no longer silent. **In source mode it also gets an icon of its own**, `app.ico` written into the install directory by `ui_kit.write_ico` and pointed at with `IconLocation`: the target is `pythonw.exe`, so with nothing said the engineer's Desktop carries Python's feather for an app that is not Python's, which is the one place rule 12 is visible to the person using it. Written rather than shipped, so there is no icon file to stage into a bundle or to keep in step with the one the app draws, and never fatal — it runs after every file that matters is on disk, and an install with a plain shortcut is an install. Exe mode passes none and needs none: a shortcut takes its icon from the exe it points at, and `package.ps1` has already stamped that exe with this same artwork.
- No Setup PIN. The live password check replaces it, and each install asks for the credential that fits it rather than for the admin password throughout (ADR-0007).
